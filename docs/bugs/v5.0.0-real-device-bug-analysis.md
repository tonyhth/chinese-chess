## Bug 1（P0）：输棋后弹出空白窗口

### 根因（一句话）
游戏结束后 `generateReviewCard()` 异步分析棋局，若 Pikafish 引擎在 iOS 上初始化失败（如 app 进过后台被 shutdown），分析结果全为 nil，`generateReviewCard()` 仍返回一个空卡片（rating=3、无质量分布、无失误记录），用户看到的内容呈现为"空白"。

### 详细分析
- `ChineseChessiOSApp.swift` 的 `onChange(of: gameViewModel.gameState)` 在游戏结束时触发 `generateReviewCard()`
- `generateReviewCard()` 内创建 `AnalysisViewModel`，调用 `analyzeAll()`
- `analyzeAll()` 检查 `EngineRouter.shared.switchEngineIfNeeded()` 返回值，若不是 `EmbeddedPikafishEngine` 则设置 `analysisUnavailableMessage` 并返回（v4.1 Bug 3 fix）
- **但存在遗漏**：若引擎对象存在但内部 NNUE 未加载成功，`analyzeMove()` 对每步返回 nil，`analysisUnavailableMessage` 不会被设置
- 最终 `generateReviewCard(analyses: [nil, nil, ...])` 返回一个 GameReviewCard（totalMoves=0, qualityDistribution=[:], biggestBlunder=nil, rating=3）
- `ReviewCardView` 渲染时：质量分布 ForEach 无内容、最大失误不显示、只剩标题+3星+"继续努力"文案 → 看起来是"空白窗口"
- 另外存在竞态风险：RankUp 弹窗 dismiss 后从 `pendingReviewRecord` 恢复 `showReviewCardSheet=true` 时，`reviewCardData` 可能已被后续逻辑置 nil

### 修复方案
1. **AnalysisViewModel.analyzeAll() 增加全 nil 检测**：分析完成后如果所有 analyses 均为 nil，设置 `analysisUnavailableMessage`
2. **generateReviewCard() 增加空卡片防护**：若 `card.totalMoves == 0`，走和引擎不可用相同的路径（设置 `reviewCardUnavailableMessage`），不弹 sheet
3. **ReviewCardView sheet 增加空状态保护**：sheet 内容加 `else` 分支显示 loading 或错误提示，避免完全空白

### 影响范围
- `AnalysisViewModel.swift`：`analyzeAll()` 末尾增加 nil 计数检查（~5 行）
- `ChineseChessiOSApp.swift`：`generateReviewCard()` 增加空卡片判断（~3 行）
- `ReviewCardView`（`CoachModeOverlay.swift`）：sheet 内容 else 分支（~5 行）
- 不影响 macOS 版本（macOS 引擎生命周期不受 scenePhase 影响）

## Bug 2（P0）：复盘过程中闪退

### 根因（一句话）
`ReplayViewModel` 的快照缓存机制存在 off-by-one 错误：`snapshot[K]` 存储的是执行完 `move[K]` 后的状态（K+1 步），但 `rebuildBoard(upTo: K)` 在 `snapIdx == index` 时直接使用该快照不做回退，导致棋盘多了一步棋；后续在损坏的棋盘状态上执行 `board.execute()` 触发崩溃。

### 详细分析
快照语义：`snapshot[20]` = 执行完 `moves[20]` 后的棋盘（即 moves[0...20] 共 21 步已执行）

`goForward()` 中 `takeSnapshotIfNeeded(at: currentIndex)` 在 `currentIndex += 1` 之前调用，所以 `currentIndex=20` 时执行完 `moves[20]` 后存入 `snapshots[20]`，此时棋盘有 21 步。

`rebuildBoard(upTo: index)` 中：
```swift
let snapIdx = (index / snapshotInterval) * snapshotInterval
if snapIdx > 0, let snap = snapshots[snapIdx] {
    startBoard = snap.snapshot()  // 已有 snapIdx+1 步
    startIndex = snapIdx + 1
}
```

当 `index == snapIdx`（即 index 是 20 的倍数：20, 40, 60...）时：
- `snapshots[snapIdx]` 存在（有 snapIdx+1 步）
- `startIndex = snapIdx + 1 > index` → 循环 `for i in snapIdx+1..<index` 为空
- 棋盘状态比期望多 1 步

后续操作（goForward/goBack）在错误棋盘上执行 `board.execute(move)`，由于 `board.piece(at: move.from)` 找不到棋子（已被多执行的移动走了），fallback 到 `move.piece`，但 `execute` 内部可能因状态不一致 crash。

### 修复方案
1. **修正 rebuildBoard 的快照边界判断**：当 `snapIdx == index` 时应使用前一个快照（`snapIdx - snapshotInterval`）从更早的状态重建
2. **或修正快照索引语义**：让 `snapshot[K]` 存储"执行完 K 步"的状态（而非执行完 `move[K]`），使索引语义一致
3. **board.execute() 增加安全检查**：execute 前验证 `piece(at: from) != nil`，若不匹配则跳过该步而非 crash

**推荐方案 1**（最小改动）：
```swift
// rebuildBoard 内部修正
let snapIdx = (index / snapshotInterval) * snapshotInterval
// 关键修正：当 index 正好是 snapshotInterval 的倍数时，退回前一个快照
let effectiveSnapIdx = (snapIdx == index && snapIdx > 0) ? snapIdx - snapshotInterval : snapIdx
```

### 影响范围
- `ReplayViewModel.swift`：`rebuildBoard(upTo:)` 增加边界修正（~3 行）
- `Board.swift`：`execute()` 增加安全检查（可选，~2 行）
- 影响所有使用 ReplayViewModel 的视图：`ReplayView`、`CoachSessionView`、残局回放

## Bug 3（P1）：复盘没有每一步的解释和说明

### 根因（一句话）
游戏结束自动弹出的 `ReviewCardView` 其"查看详情"按钮的 `onViewDetail` 回调在 iOS 上只关闭 sheet，未导航到 `CoachSessionView`，导致用户无法从复盘卡片进入逐步讲解；且 `CoachSessionView` 内 `AnalysisViewModel.analyzeStep()` 默认跳过 AI 走法（`isPlayerMove` 过滤），用户在逐步浏览时 AI 回合无讲解内容。

### 详细分析
两层问题：

**Layer 1 — 入口断裂**：
`ChineseChessiOSApp.swift` 中 ReviewCardView 的回调：
```swift
ReviewCardView(
    card: card,
    onViewDetail: {
        showReviewCardSheet = false  // 只关闭，没有打开 CoachSessionView
    },
    onClose: {
        showReviewCardSheet = false
    }
)
```
对比 macOS 版本，需要验证 macOS 是否也只做关闭。如果 macOS 从 ReviewCard 进入 Coach 的路径也断了，这是双平台 bug。

**Layer 2 — 分析覆盖不完整**：
`AnalysisViewModel.analyzeStep(index)` 中：
```swift
if !force && !isPlayerMove(at: index) { return }
```
这导致 AI 走法（奇数 index 或偶数 index，取决于先手方）不被分析。`CoachSessionView` 的 `showExplanation(for: index)` 在 AI 回合时 `analyses[index]` 为 nil，直接 return，不展示讲解。

### 修复方案
1. **修复 ReviewCardView 入口**：`onViewDetail` 回调改为：关闭 ReviewCard sheet → 打开 ReplayView（传入当前 gameRecord）→ 自动进入 CoachSessionView。或直接从 ChineseChessiOSApp 弹出 CoachSessionView sheet
2. **CoachSessionView 默认分析所有步**：在 CoachSessionView 的 `analyzeGame()` 中调用 `analysisVM.analyzeStep(i, force: true)`，强制分析包括 AI 走法的所有步骤
3. **UI 补充说明**：在讲解卡片中标注"你的走法"/"AI的走法"，让用户知道每步是谁走的

### 影响范围
- `ChineseChessiOSApp.swift`：修改 `onViewDetail` 回调逻辑（~10 行，可能需要新增 sheet 状态）
- `CoachSessionView.swift`：`analyzeGame()` 改用 force: true（~1 行修改）
- `AnalysisViewModel.swift`：无改动（方法已支持 force 参数）
- 可能需要同步修改 macOS 版本 `ChineseChessApp.swift`

## Bug 4（P1）：残局数据完整性（第27局无将帅，第9局无将）

### 根因（一句话）
残局数据本身完整（Luke 扫描确认），问题出在 `PuzzleSelectView` 的列表排序与 `Puzzle.name` 编号不保证一致：`filteredPuzzles` 经过分类筛选 + 排序后，显示顺序可能与 `puzzle.id` 顺序不同，用户看到的"第27局"是列表中的第 27 个，但不一定对应数据中 id=27 的残局。

### 详细分析
`PuzzleSelectView.filteredPuzzles` 经过五重过滤：
1. 分类筛选
2. 难度筛选
3. 搜索筛选
4. 通关状态筛选
5. 排序（未通关在前，按 id 排）

排序逻辑：
```swift
case .uncompleted, .all:
    if aDone != bDone { return !aDone }
    return a.id < b.id
```

当用户切换筛选条件后，列表内容变化。用户说"第27局"，但这个"27"是列表位置还是 puzzle.name 中的编号，无法确认。如果 `puzzle.name` 格式为"第N局"，那 name 和 id 应该一致。但如果筛选过滤掉了某些残局，列表中第 27 行可能不是 id=27。

另外，`PuzzleViewModel.init` 使用 `Board(fen: puzzle.initialFEN)` 创建棋盘。如果 iOS 上 `Board(fen:)` 解析有边界问题（Luke 的 FENDecoder 校验通过，但 Board 构造器可能有不同实现），可能导致某些 FEN 字段被忽略。

第三种可能：`ChessBoardView` 渲染在特定屏幕尺寸下，棋盘边缘的将帅位置（九宫格角落）被 `cornerRadius` 或 `padding` 裁剪。

### 修复方案
1. **验证列表编号**：在 `PuzzleRow` 中显示 `puzzle.id` 编号（如"#27"），让用户能准确报告是哪个残局
2. **Board(fen:) 防御性检查**：构造完成后断言 `pieces.count >= 2`（至少有双方将帅），log 输出解析结果
3. **渲染边界检查**：确认 `BoardSizing.padding` 在小屏幕上不会裁剪九宫格内的棋子

### 影响范围
- `PuzzleSelectView.swift`：PuzzleRow 增加编号显示（~2 行）
- `Board.swift`：构造后增加完整性断言（~3 行）
- `BoardSizing.swift`：验证 padding 在各屏幕尺寸下是否足够（检查，可能无需改）
- **优先级降低**：需要真机截图确认具体是哪个残局、是否真的渲染缺失

## Bug 5（P2）：UI 重复——级别选择

### 详细分析
**顶部入口**（`ToolbarView.swift` iOS 分支）：

// v3.7.1 B2: iOS 难度快捷按钮

## Bug 6（P1）：判和逻辑 bug — 连续悔棋后判和

### 根因（一句话）
`GameViewModel.undoMove()` 撤销棋步时移除了 `gameMoves` 和 `board.moveHistory` 的记录，但**未清理 `positionFingerprints` 字典**，导致悔棋后重走相同路线时同一局面的 fingerprint 计数累积到 ≥3，触发 `checkGameState()` 中的三次重复判和。

### 详细分析
走棋流程：
```swift
func movePiece(...) {
    ...
    board.execute(move)
    ...
    recordPositionFingerprint()  // ← 记录局面 fingerprint
    checkGameState()              // ← 检查三次重复
    ...
}
```

悔棋流程：
```swift
func undoMove() {
    ...
    board.undoLastMove()          // 撤销棋盘
    gameMoves.removeLast()        // 移除走法记录
    // ❌ 没有清理 positionFingerprints！
    halfmoveClock = lastMove.halfmoveClock  // halfmoveClock 有恢复
    ...
    // ❌ 没有调用 checkGameState()，但这不是问题
}
```

复现场景：
1. 玩家走 A → AI 走 B → 玩家走 C → AI 走 D → 局面 PD
   - `fingerprints[PD] = 1`
2. 玩家悔棋（撤销 D+C）→ 棋盘回到局面 PC
3. 玩家再走 C → AI 走 D → 局面 PD
   - `fingerprints[PD] = 2`（旧的计数还在！）
4. 再悔棋再重走 → `fingerprints[PD] = 3` → **判和！**

`checkGameState()` 中的三次重复检测：
```swift
let count = positionFingerprints[boardFingerprint(), default: 0]
if count >= 3 {
    gameState = .draw  // ← 误判
    return
}
```

### 修复方案
在 `undoMove()` 中，移除被撤销步骤的 fingerprint 记录：

```swift
func undoMove() {
    ...
    // 撤销 AI 步
    if let aiMove = board.undoLastMove() {
        removeCapturedRecord(for: aiMove)
        if !gameMoves.isEmpty { gameMoves.removeLast() }
        // 移除该步对应的 fingerprint
        removeLastFingerprint()
    }
    // 撤销玩家步
    if let playerMove = board.undoLastMove() {
        removeCapturedRecord(for: playerMove)
        if !gameMoves.isEmpty { gameMoves.removeLast() }
        removeLastFingerprint()
    }
    ...
}

private func removeLastFingerprint() {
    let fp = boardFingerprint()
    positionFingerprints[fp, default: 0] -= 1
    if positionFingerprints[fp] ?? 0 <= 0 {
        positionFingerprints.removeValue(forKey: fp)
    }
}
```

注意：`undoLastMove()` 执行后 `board` 已回退到前一个状态，此时 `boardFingerprint()` 生成的是撤销后的局面，不是被撤销的局面。需要在 undo 之前记录当前 fingerprint，undo 后减去该计数。

**修正实现**：
```swift
func undoMove() {
    ...
    let fpBeforeUndo = boardFingerprint()  // 撤销前的局面
    
    if let aiMove = board.undoLastMove() {
        removeCapturedRecord(for: aiMove)
        if !gameMoves.isEmpty { gameMoves.removeLast() }
    }
    if let playerMove = board.undoLastMove() {
        removeCapturedRecord(for: playerMove)
        if !gameMoves.isEmpty { gameMoves.removeLast() }
    }
    
    // 回退 fingerprint：当前局面（undo 后）的计数减 1
    // 因为 recordPositionFingerprint 是在走棋后记录的，
    // undo 两次 = 撤销两次 recordPositionFingerprint
    let currentFP = boardFingerprint()
    positionFingerprints[currentFP, default: 0] -= 1
    if positionFingerprints[currentFP] ?? 0 <= 0 {
        positionFingerprints.removeValue(forKey: currentFP)
    }
    
    ...（其余不变）
}
```

Wait, 更精确的做法：`recordPositionFingerprint()` 在每步走完后调用，记录走完后的局面。所以 undo 两步后，需要移除最后 2 个 fingerprint 记录。

最简洁方案：**undo 后重建 positionFingerprints**：

```swift
func undoMove() {
    ...（现有的 undo 逻辑）
    
    // 重建 fingerprint 历史
    positionFingerprints.removeAll()
    let tempBoard = Board()
    recordFingerprint(for: tempBoard)  // 初始局面
    for move in gameMoves {
        tempBoard.execute(Move(piece: move.piece, from: move.from, to: move.to, captured: move.captured))
        let fp = FENParser.generate(board: tempBoard)
        positionFingerprints[fp, default: 0] += 1
    }
}
```

但这是 O(n) 的。对于正常对局（<200 步）影响不大。

**推荐方案**：使用更简单的增量方式 — 在 undo 之前记录当前 fingerprint，undo 后减去计数。

### 影响范围
- `GameViewModel.swift`：`undoMove()` 增加 fingerprint 清理（~10 行）
- 不影响其他文件
- 同步检查 `PuzzleViewModel` 的 `positionHistory` 是否有相同问题（看代码，PuzzleViewModel 使用数组 `[String]` 而非计数字典，undo 时直接移除最后两个即可，但其 undo 也未清理 — 这是另一个潜在 bug）
