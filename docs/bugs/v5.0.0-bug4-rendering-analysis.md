# Bug 4 追加分析：残局棋子不可见（v4.0.0 回归）

> **架构师**: Alex  
> **日期**: 2025-07-23  
> **回归版本**: v4.0.0（v3.9.1 正常）

---

## 根因（一句话）

`PuzzleSelectView` 通过 `.sheet` 呈现，其内部 `.fullScreenCover(item: $selectedPuzzle)` 打开 `PuzzlePlayView`——在 iOS 上 **sheet 内嵌套 fullScreenCover** 时，首次 layout pass 中 GeometryReader 可能返回异常 size（接近 zero），导致 `BoardSizing.calculate()` 计算出零或负的 cellSize/padding，棋子渲染在不可见位置或尺寸为零；v4.0.0 统一 sheet 管理引入了此嵌套结构。

## 容器嵌套链（已确认）

```
ChineseChessiOSApp
  └─ NavigationStack
       └─ .sheet(item: $activeSheet)               ← 第 1 层：sheet
            └─ case .puzzles: PuzzleSelectView()
                 └─ .fullScreenCover(item: $selectedPuzzle)  ← 第 2 层：嵌套 fullScreenCover
                      └─ PuzzlePlayView
                           └─ VStack {
                               titleBar           ← ~90pt（含返回/标题/步数/模式切换）
                               ChessBoardView     ← GeometryReader + .aspectRatio(8/9, .fit)
                               bottomArea         ← frame(maxHeight: screenHeight * 0.20~0.25)
                             }
```

**对比**：主对弈页面的 ChessBoardView 直接在 NavigationStack 内，无 sheet 包裹，GeometryReader 拿到的 size 稳定。ReplayView 通过顶层 `.fullScreenCover(item: $toolbarReplayRecord)` 呈现，也不嵌套在 sheet 内——所以主页面和回放都不出问题。

## BoardSizing 关键参数（子代理报告）

- `gridCols = 8`，`gridRows = 9`
- `maxCellSize = 80`
- iOS: `maxBoardWidth = 600`，`maxBoardHeight = 675`
- `calculate(width:height:)` 使用 **迭代收敛** 计算 padding/cellSize

如果传入的 width 或 height 为 0 或极小值（如 sheet→fullScreenCover 首次 layout pass），迭代收敛可能：
- cellSize → 0
- padding → 占满整个空间
- 棋子 `.position()` 计算出棋盘外坐标或尺寸为零

## 为什么不是所有残局都受影响？

棋盘渲染异常是 **尺寸依赖** 的，不是数据依赖的：
- 在大屏 iPhone（如 Pro Max）上 sheet→fullScreenCover 的 geometry 可能正常
- 在小屏 iPhone SE 上 geometry 被挤压更严重
- 某些残局棋子分布集中在中部，即使 cellSize 偏小仍部分可见；将帅在九宫格角落（row 0/row 9），最先被裁剪

## 排除项

1. **数据完整性**：Luke 已确认 551 局 FEN 全部通过 FENDecoder 校验 ✅
2. **Board(fen:) 解析失败**：若解析失败 fallback 到 `Board()`（标准开局 32 子），洪涛会看到全部棋子而非"缺将帅" ✅
3. **board 被意外重置**：PuzzlePlayView/PuzzleViewModel 无 onAppear/task 覆盖 board ✅
4. **ChessBoardView 渲染逻辑**：`ForEach(board.pieces)` 无过滤，board 有什么就画什么 ✅

## 为什么 v4.0.0 回归？

代码注释 `// v3.8.0 Phase 4 #4: 统一 sheet — 与 macOS 对齐` 表明 sheet 管理在 v3.8~v4.0 期间统一。v3.9.1 及之前，PuzzleSelectView 可能通过 NavigationLink push 呈现（不涉及 sheet→fullScreenCover 嵌套）。v4.0.0 统一为 `.sheet` 后引入了嵌套结构。

同时 `PuzzleSelectView` 已标记 `@available(*, deprecated, message: "Use ChapterSelectView as top-level entry")`，说明迁移到 ChapterSelectView 的工作未完成，仍在使用旧路径。

## 修复方案（三层防御）

### 方案 1：消除 sheet → fullScreenCover 嵌套（根因修复）

将 `PuzzlePlayView` 的呈现从 `PuzzleSelectView` 内部移到 `ChineseChessiOSApp` 顶层：

```swift
// ChineseChessiOSApp.swift 顶层新增
@State private var selectedPuzzle: Puzzle?

.fullScreenCover(item: $selectedPuzzle) { puzzle in
    PuzzlePlayView(puzzle: puzzle)
}

// case .puzzles 传回调
case .puzzles:
    PuzzleSelectView(onPuzzleSelected: { puzzle in
        activeSheet = nil        // 关闭 sheet
        DispatchQueue.main.async {
            selectedPuzzle = puzzle  // 顶层 present fullScreenCover
        }
    })
```

`PuzzleSelectView` 内部移除 `.fullScreenCover`，改为通过回调通知。

### 方案 2：BoardSizing.calculate 增加最小尺寸保护

```swift
static func calculate(width: CGFloat, height: CGFloat) -> Sizing {
    let safeWidth = max(width, 200)   // 最小 200pt
    let safeHeight = max(height, 200)
    // ... 现有逻辑使用 safeWidth/safeHeight
}
```

### 方案 3：ChessBoardView GeometryReader 增加守卫

```swift
GeometryReader { geo in
    if geo.size.width < 10 || geo.size.height < 10 {
        // 首次 layout pass size 异常，渲染空视图等待二次 layout
        Color.clear
    } else {
        // 正常渲染
        let sizing = BoardSizing.calculate(width: geo.size.width, height: geo.size.height)
        ...
    }
}
```

**建议方案 1 + 方案 2 同时执行**：方案 1 消除根因，方案 2 防御未来类似问题。

## 影响范围

| 文件 | 改动量 | 说明 |
|------|--------|------|
| `PuzzleSelectView.swift` | ~15 行 | 移除 fullScreenCover，新增 onPuzzleSelected 回调 |
| `ChineseChessiOSApp.swift` | ~10 行 | 新增 selectedPuzzle 状态 + 顶层 fullScreenCover |
| `BoardSizing.swift` | ~3 行 | calculate 增加最小尺寸保护 |
