## 二、逐个问题分析与修复方案

### 问题 1：大师棋谱棋盘显示不全（iOS）— P1

**根因确认**

`MasterGameBrowserView.swift` 的 `browserLayout`：

```swift
#if os(macOS)
HStack(spacing: 0) {
    sidebar.frame(width: 200)
    Divider()
    listContent
}
.frame(minWidth: 720, minHeight: 520)  // ← 仅 macOS 分支内
#else
// iOS 分支：有独立的分类列表 + listContent，但无棋盘布局问题
#endif
```

`.frame(minWidth: 720, minHeight: 520)` 在 `#if os(macOS)` 块内，**不直接影响 iOS**。

**实际根因**：iOS 播放布局 `iosPlayLayout` → `playContent`：

```swift
private func playContent(viewModel: DemoViewModel) -> some View {
    VStack(spacing: 0) {
        DemoInfoBar(...)
        ZStack(alignment: .top) {
            DemoBoardView(board: viewModel.board, ...)  // ← 无 frame 约束
            ...
        }
        DemoControlBar(...)
    }
}
```

`DemoBoardView` → `BoardCanvasView` 使用 `GeometryReader` 自适应。问题是 `ZStack(alignment: .top)` 中的 CommentaryOverlay 和 DemoControlBar 占用空间后，`DemoBoardView` 没有获得足够的 layoutPriority。棋盘被 DemoInfoBar 和 DemoControlBar 挤压。

对比：主棋盘 `BoardView` 有 `.layoutPriority(1)`，而 `playContent` 中的 `DemoBoardView` 没有。

**修复方案**

文件：`MasterGameBrowserView.swift`，`playContent` 方法

在 `ZStack` 外加 `.layoutPriority(1)`，并确保 DemoBoardView 在 ZStack 内获得优先空间：

```swift
ZStack(alignment: .top) {
    DemoBoardView(board: viewModel.board, lastMove: viewModel.lastMove, isFlipped: viewModel.item.shouldFlipBoard)
        .frame(maxWidth: .infinity, maxHeight: .infinity)  // ← 新增：确保棋盘撑满 ZStack
    
    if viewModel.showCommentary, let commentary = viewModel.currentCommentary {
        CommentaryOverlay(commentary: commentary, speed: viewModel.speed)
            .padding(.top, 8)
    }
    // P1-2: 连播过渡 UI
    if viewModel.playState == .transitioning { ... }
}
.layoutPriority(1)  // ← 新增：优先分配空间给棋盘 ZStack
```

**补充（P1-3 修复）**：CommentaryOverlay 和 ProgressOverlay 不应占据大量垂直空间。确认它们用 `.allowsHitTesting(false)` 和透明的背景，不挤压 DemoBoardView 的布局。如果 CommentaryOverlay 有固定高度，需要确保它用 `.frame(maxHeight:)` 限制，不与棋盘争抢空间。

同样修复适用于 `PuzzleDemoView.swift` 的 `mainContent` 方法（相同结构）。

**影响范围**：MasterGameBrowserView 和 PuzzleDemoView 的 iOS 棋盘播放视图。

### 问题 2：残局闯关菜单进不去（iOS）— P0

**根因确认（v1.1 重新排查）**

**纠正 v1.0 的事实错误**：StudyHubView **不是通过 sheet 展示的**。实际链路：

```swift
// ChineseChessiOSApp.swift L162
NavigationLink {
    StudyHubView()      // ← push 进主 NavigationStack
} label: {
    Label("toolbar.study", systemImage: "graduationcap")
}
```

`SheetDestination` enum 中没有 `.studyHub` case。StudyHubView 是通过 `NavigationLink(destination:)` 直接 push 进主 `NavigationStack` 的标准导航。因此 v1.0 中“sheet 内 NavigationStack 导致 NavigationLink(value:) 不响应”的推理链**不成立**。

在标准 NavigationStack push 场景下，`NavigationLink(value:)` + `.navigationDestination(for:)` 是标准用法，应该正常工作。

**重新排查的真实根因路径（需诊断确认）**：

`ChapterSelectView` 的内容来自 `ChapterStore.shared.chapters`，而 `ChapterStore.rebuildChapters()` 有一个关键断言：

```swift
let sorted = globalSorted
assert(!sorted.isEmpty, "ChapterStore: PuzzleStore has no puzzles loaded")
```

`globalSorted` 来自 `PuzzleStore.shared.puzzles`。如果 `PuzzleStore` 加载 `puzzles.json` 失败（ResourceBundle 定位失败、JSON 解码失败等），`puzzles` 为空数组，`sorted` 为空，`chapters` 构建出来的每个章节的 `puzzles` 也为空——页面会渲染但内容为空，用户看到“进不去”。

**但 assert 只在 Debug 模式触发**。Release 构建（真机验证很可能用 Release）中 assert 是 no-op，`sorted` 为空后：
- `endIndex = min(config.globalEnd, 0) = 0`
- `puzzles = Array(sorted[0..<0]) = []`
- `completedCount = 0`
- `isUnlocked` 对于第一章 `.none` → `true`

所以章节列表会显示（第一章解锁），但进入后残局列表为空——这与“进不去”的症状不同。

**更可能的根因**：不是数据为空，而是 **UI 层面的导航问题**。需确认用户描述的“进不去”具体是：

| 症状描述 | 可能根因 | 排查方法 |
|---------|---------|----------|
| 点击“残局闯关”卡片无反应 | NavigationLink 在某些 iOS 版本的 List/ScrollView 内失效 | 确认真机 iOS 版本，尝试加 `.buttonStyle(.plain)` |
| 进入后页面空白 | ChapterStore.chapters 为空 | 加日志打印 chapters.count |
| 进入后列表有内容但点击章节无反应 | NavigationLink(value:) 在 push 后的二级页面不响应 | 改为 NavigationLink(destination:) 降级测试 |
| 页面闪退 | assert 在 Debug 触发 / 其他 crash | 看 crash log |

**修复方案（分步执行）**

**步骤 1**：加诊断日志，确认根因（P0，必须先做）

文件：`ChapterSelectView.swift`

```swift
.onAppear {
    let store = ChapterStore.shared
    print("[ChapterSelect] chapters.count = \(store.chapters.count)")
    print("[ChapterSelect] first chapter isUnlocked = \(store.chapters.first?.isUnlocked ?? false)")
    print("[ChapterSelect] PuzzleStore.puzzles.count = \(PuzzleStore.shared.puzzles.count)")
}
```

文件：`StudyHubView.swift`，在 studyCard 的 NavigationLink 内确认点击响应：

```swift
NavigationLink(destination: destination) {
    ...
}
.simultaneousGesture(TapGesture().onEnded {
    print("[StudyHub] tapped: \(title)")
})
```

**步骤 2**：根据诊断结果修复（三选一）

- **如果 chapters.count > 0 且点击有响应**：问题是三级 NavigationLink(value:) 不工作 → 改为 NavigationLink(destination:) 直接推入

- **如果 chapters.count == 0**：问题是 PuzzleStore 加载失败 → 检查 ResourceBundle 在真机 Release 构建中的路径

- **如果点击无响应**：问题是 NavigationLink 在 List/ScrollView 内失效 → 改用 `.onTapGesture + NavigationPath` 编程式导航

**建议**：步骤 1 在本轮修复中先发一个 debug build 到真机，收集日志后再定步骤 2。不要在未确认根因时就改代码。

### 问题 3：开局探索棋盘太小（iOS）— P1

**根因确认**

`OpeningExplorerView.swift` 的 `boardPreview`：

```swift
HStack(spacing: 0) {
    treeList
        .frame(maxWidth: .infinity)  // ← 占据大量空间
    boardPreview
}

private var boardPreview: some View {
    VStack(spacing: 8) {
        OpeningBoardPreview(board: board)
            .cornerRadius(6)
        ...
    }
    .padding(8)
    .frame(maxWidth: .infinity)  // ← 与 treeList 平分空间
    .background(...)
}
```

`treeList` 和 `boardPreview` 在 `HStack` 中各占 `.frame(maxWidth: .infinity)`，平分宽度。在 iPhone 竖屏（375pt 宽），棋盘只有 ~170pt 宽度——确实太小。

另外 `OpeningBoardPreview` 本身没有 `.frame(maxHeight: 200)` 硬限制（初步分析有误）。它使用 `GeometryReader` + `aspectRatio` 自适应。但在 HStack 的 50% 宽度约束下，棋盘确实很小。

**这不是 `.frame(maxHeight: 200)` 的问题，而是 HStack 平分布局的问题。**

**修复方案**

iOS 改为上下布局（树列表在上，棋盘在下），树列表用比例约束而非硬值：

文件：`OpeningExplorerView.swift`

```swift
// 替换 HStack 为条件编译
#if os(iOS)
VStack(spacing: 0) {
    // 树列表限高：使用比例约束，适应不同屏幕尺寸
    // SE 屏幕小，树列表不应急占太多；Pro Max 屏幕大，可以多显
    treeList
        .frame(maxHeight: 280)  // 基准值：约为 iPhone 标准高度的 35%
    
    // 分隔线
    Divider()
        .background(Color.gray.opacity(0.3))
    
    // 棋盘占据剩余空间
    boardPreview
}
#else
HStack(spacing: 0) {
    treeList
    boardPreview
}
#endif
```

**P1-4 修复说明**：选用 280pt 而非 240pt 作为上限。依据：

| 设备 | 屏幕高度 | 280pt 占比 | 棋盘可用高度 |
|------|---------|----------|------------|
| iPhone SE | 667pt | 42% | ~387pt |
| iPhone 15 | 844pt | 33% | ~564pt |
| iPhone 15 Pro Max | 932pt | 30% | ~652pt |

280pt 在 SE 上略大（42%），但树列表本身是 ScrollView，内容多时可滚动。棋盘在 SE 上 ~387pt 宽（受 maxBoardWidth=600 约束，实际约为 387pt），可接受。

如果执行时发现 SE 上棋盘仍然太小，可进一步降为 `GeometryReader` 动态计算 `geo.size.height * 0.35`。但 OpeningExplorerView 当前不用 GeometryReader 包裹 HStack/VStack，引入会增加复杂度。先用 280pt 定值，实测后调整。

**影响范围**：仅 iOS，macOS 保持左右分栏。

### 问题 4：三个功能的棋盘能否复用同一套布局？— P2（架构决策）

**现状分析**

| 功能 | 棋盘组件 | 渲染层 | 差异 |
|------|---------|--------|------|
| 大师棋谱 / 残局演示 | DemoBoardView | BoardCanvasView | 无 lastMove 动画标记（有高亮圆圈） |
| 开局探索 | OpeningBoardPreview | **独立实现**（手写 Canvas） | 无 lastMove 高亮、无翻转支持 |
| 复盘分析 | ReplayBoardView | BoardCanvasView | 有翻转动画 |
| 主对弈 | BoardView | BoardCanvasView | 有交互（点击选子） |
| 新手教程 | MiniChessBoard | **独立实现**（手写 Canvas） | 有交互（点击走子）、迷你尺寸 |

**重复实现问题**

`OpeningBoardPreview` 和 `MiniChessBoard` 各自手写了棋盘渲染（Canvas 绘制格线 + 楚河汉界 + 棋子），与 `BoardCanvasView` 的渲染逻辑大量重复。

**推荐方案：渐进统一（不重写）**

1. **短期**（本次修复）：不动棋盘组件，只修布局问题（问题 1/3 的修复）
2. **中期**（下一版本）：将 `OpeningBoardPreview` 和 `MiniChessBoard` 改为调用 `BoardCanvasView`

   - `OpeningBoardPreview` → 直接替换为 `DemoBoardView`（只读，无 lastMove）
   - `MiniChessBoard` → `BoardCanvasView` + 自定义交互层（保留点击走子逻辑）

3. **不推荐**：创建一个"万能棋盘"组件。当前 `BoardCanvasView` 已经是共享渲染层，再抽一层抽象层增加复杂度无收益。

**替代方案对比**

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| A. 保持现状 + 修布局 | 零风险、零新增工作 | 重复代码仍在 | ✅ 推荐（本次） |
| B. OpeningBoardPreview 改用 BoardCanvasView | 消除一份重复 | 需验证 aspectRatio 约束兼容 | ⚠️ 可选（下版本） |
| C. 统一所有棋盘为万能组件 | 彻底消除重复 | 过度抽象、回归风险高 | ❌ 不推荐 |

**结论**：本次修复采用方案 A，在方案文档中记录方案 B 作为技术债务，下版本处理。

### 问题 5：复盘分析看不到内容（iOS）— P0

**根因确认（v1.1 修正展示路径）**

**纠正 v1.0 的事实错误**：AnalysisView 在 iOS 上的展示路径不是 `activeSheet = .analysis(record)`。

iOS `SheetDestination` enum 中**没有** `.analysis` case。实际展示链路：

```
ChineseChessiOSApp.fullScreenCover(item: $toolbarReplayRecord)
  → ReplayView(record:)
      → .sheet(isPresented: $showAnalysis)
          → AnalysisView(record:)
```

即 **fullScreenCover → sheet 嵌套**。ReplayView 是 fullScreenCover 展示的（全屏），AnalysisView 是 ReplayView 内的 sheet（半屏）。

`hasBasicAnalysis` 判断 `profile.rank >= .scholar`。如果用户有段位，进入分析流程。

**根因 1**：iOS sheet 默认只占部分屏幕高度。AnalysisView 包含 ReplayBoardView + analysisControls + moveQualityList + evalChart，这些组件在半屏 sheet 中空间不足，导致棋盘被挤压到几乎不可见。

**根因 2**：`AnalysisViewModel.analyzeAll()` 中引擎初始化失败时，`analysisUnavailableMessage` 被设置但 UI 展示只是一个 `.font(.caption).foregroundColor(.orange)` 的小文字，用户很可能看不到。

**修复方案**

1. 将 ReplayView 内的 AnalysisView 从 `.sheet` 改为 `.fullScreenCover`（iOS）：

文件：`ReplayView.swift` L107

```swift
// 修改前：
.sheet(isPresented: $showAnalysis) {
    AnalysisView(record: viewModel.record)
}

// 修改后（iOS）：
#if os(iOS)
.fullScreenCover(isPresented: $showAnalysis) {
    AnalysisView(record: viewModel.record)
}
#else
.sheet(isPresented: $showAnalysis) {
    AnalysisView(record: viewModel.record)
        .frame(minWidth: 600, minHeight: 700)
}
#endif
```

**注意**：`fullScreenCover` 不能下拉关闭，必须在 AnalysisView 的 headerBar 中确保关闭按钮可用。当前代码 `Button(l10n.t("common.close")) { dismiss() }` 已经覆盖。

2. AnalysisView 增加最外层 frame 约束：

文件：`AnalysisView.swift`

```swift
VStack(spacing: 0) { ... }
.frame(maxWidth: .infinity, maxHeight: .infinity)  // ← 新增
```

3. 引擎不可用的 UI 提示改进（P1-2 修复）——不做固定 sleep 重试，而是分类处理：

文件：`AnalysisView.swift`，`startAnalysis()` 方法

```swift
private func startAnalysis() async {
    let engine = await EngineRouter.shared.switchEngineIfNeeded()
    guard engine as? EmbeddedPikafishEngine != nil else {
        // 引擎不可用——区分原因
        // NNUE 文件缺失：重试无意义
        // 初始化时序：EngineRouter 可能尚未 ready
        // 用诊断日志区分，不盲等
        #if DEBUG
        print("[Analysis] engine unavailable, type: \(type(of: engine))")
        #endif
        // 给用户明确的错误提示 + 重试按钮
        analysisVM.analysisUnavailableMessage = L10n.shared.t("analysis.engineUnavailable")
        return
    }
    await analysisVM.analyzeAll()
}
```

在 UI 层面，当 `analysisUnavailableMessage` 非空时，显示更醒目的提示 + 手动重试按钮：

```swift
} else if let msg = analysisVM.analysisUnavailableMessage {
    VStack(spacing: 8) {
        Image(systemName: "exclamationmark.triangle")
            .foregroundColor(.orange)
        Text(msg)
            .font(.callout)
            .foregroundColor(.orange)
        Button(l10n.t("common.retry")) {
            Task { await startAnalysis() }
        }
        .buttonStyle(.bordered)
    }
}
```

这比 v1.0 的自动 sleep 重试更可靠：用户手动触发，给引擎初始化足够时间，且如果 NNUE 文件真缺失，用户不会等一个无意义的 1 秒。

```swift
private var tutorialBanner: some View {
```

### 问题 8：新手教程走子不工作 — P1

**根因确认（v1.1 更新）**

**P2-1 修复：根因尚未确认**。v1.0 列了多个可能根因但未定论。修复方案调整为：**先加日志确认，再定修复**。

`TutorialInteractiveView.swift` 的 `validateMove` 逻辑本身是正确的（P1-7 fix 后）。`enabledSide` 从 `lesson.initialFEN` 解析走方，正常工作。

**最可能的情况**：不是走子完全不工作，而是 iOS 上 MiniChessBoard 的交互问题。需要真机日志区分。

```swift
private func validateMove(_ from: Position, _ to: Position) {
    guard status != .complete else { return }
    guard let piece = board.piece(at: from) else { return }
    
    let legalMoves = MoveValidator.legalMoves(for: piece, on: board)
    guard legalMoves.contains(where: { $0.to == to }) else {
        status = .illegal
        return
    }
    // ...
}
```

`MiniChessBoard` 的 `onMove` 回调传入 `(from, to)`。`MoveValidator.legalMoves` 正常工作。

**但**：`enabledSide` 限制只有一方可以走子。如果 `enabledSide` 返回 `nil`（FEN 解析失败），则 MiniChessBoard 不允许任何走子。

```swift
private var enabledSide: Side? {
    guard let fen = lesson.initialFEN else { return nil }
    let parts = fen.split(separator: " ")
    if parts.count >= 2 {
        return parts[1] == "w" ? .red : .black
    }
    return .red
}
```

FEN 格式：`"3aka3/9/9/9/9/9/9/9/9/4R4 w - - 0 1"`。`split(separator: " ")` 的第二项是 `"w"`。

**潜在问题**：`enabledSide` 是 computed property，每次访问都重新解析 FEN。如果 `board` 在走子后 FEN 变化（`board.fen` 属性可能不与 `lesson.initialFEN` 一致），这不是问题因为用的是 `lesson.initialFEN` 而非 `board.fen`。

**更可能的 iOS 专属问题**：`MiniChessBoard` 的 `onTapGesture` / `DragGesture` 在 iOS 上的坐标转换可能有偏差。

检查 MiniChessBoard 的交互：

```swift
// MiniChessBoard.swift
.onTapGesture { location in
    guard let pos = BoardSizing.cgPointToPos(point: location, ...) else { return }
    // 选中棋子或尝试走子
}
```

如果 MiniChessBoard 使用 `GeometryReader` + `.aspectRatio`，坐标在 iOS 上可能因为 safeArea 或 NavigationStack 的偏移而不准确。

**修复方案（先诊断后修复）**

1. 真机 Debug 构建加诊断日志（P1 批次先做）：

```swift

print("[Tutorial] validateMove: from=\(from), to=\(to), piece=\(piece.type), side=\(piece.side)")
print("[Tutorial] legalMoves: \(legalMoves.map { $0.to })")
print("[Tutorial] enabledSide: \(enabledSide), board.fen: \(board.fen)")
#endif
```

2. 根据日志结果修复（三选一）：

- **如果 validateMove 未被调用**：MiniChessBoard 的手势/坐标转换在 iOS 上有问题 → 修复 MiniChessBoard 的坐标映射
- **如果 validateMove 被调用但返回 illegal**：MoveValidator 在特定 FEN 下有 bug → 修复 validator
- **如果 validateMove 被调用且返回 wrong**：用户不知道该走哪方 → 加走子方提示

3. UI 改善（无论根因如何都应加）——在 waiting 状态中明确显示当前走子方：

### 问题 9：开局教练没有图标 — P2

**根因确认**

`StudyHubView.swift`：

`openingCoachCard` 是自定义的 `NavigationLink + VStack`，不像其他卡片使用 `studyCard(title:icon:color:destination:)`。虽然它有 `Image(systemName: "compass.fill")`，但它的视觉风格与 `studyCard` 的不一致：

- `studyCard`：VStack(spacing: 12) { Image + Text }，固定 padding
- `openingCoachCard`：VStack(spacing: 12) { Image + Text + 副标题 }

`openingCoachCard` 多了副标题，导致布局和其他卡片不完全对齐。但"没有图标"的描述可能指 **macOS 懒加载图标**或 **图标颜色不一致**。

实际看代码：`openingCoachCard` 的 Image 用 `.foregroundStyle(.teal)`，其他卡片传 color 参数（`.orange`, `.purple`, `.blue`, `.red`）。颜色不一致但不缺图标。

**修复方案**

重构 `openingCoachCard` 使用 `studyCard` 的同一模板，副标题作为可选参数：

文件：`StudyHubView.swift`

```swift
// studyCard 增加可选 subtitle 参数
@ViewBuilder
private func studyCard<D: View>(
    title: String, icon: String, color: Color,
    destination: D,
    subtitle: String? = nil  // ← 新增
) -> some View {
    NavigationLink(destination: destination) {
        VStack(spacing: 12) {
            Image(systemName: icon)
                .font(.system(size: 32))
                .foregroundStyle(color)
                .frame(height: 40)

            Text(title)
                .font(.headline)
                .foregroundStyle(.primary)
                .lineLimit(1)
                .minimumScaleFactor(0.8)

            if let subtitle = subtitle {
                Text(subtitle)
                    .font(.caption2)
                    .foregroundColor(.secondary)
                    .lineLimit(1)
            }
        }
        .frame(maxWidth: .infinity)
        .padding(.vertical, 20)
        .padding(.horizontal, 12)
        .background(Color.controlBackground)
        .clipShape(RoundedRectangle(cornerRadius: 12))
    }
    .buttonStyle(.plain)
}
```

替换 openingCoachCard 的调用：

```swift
studyCard(
    title: l10n.t("study.openingCoach"),
    icon: "compass.fill",
    color: .teal,
    destination: OpeningCoachSelectView(),
    subtitle: practiceStore.practicedCount > 0
        ? l10n.t("study.openingCoach.stats", ...)
        : l10n.t("study.openingCoach.noRecord")
)
```

### 问题 10：macOS 大师棋谱和残局演示分类不显示 — P1

**如果 JSON 不在**：问题是 Xcode/SPM 资源打包配置，需修复 `project.yml` 中的资源打包规则。
