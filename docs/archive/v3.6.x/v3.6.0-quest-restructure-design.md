## 一、设计概述

### 1.1 目标

将现有 4 套割裂系统（残局/段位/成就/每日挑战）整合为「闯关→升级→解锁→再闯关」的闭环。

### 1.2 核心设计原则

1. **章节是 UI 层概念，不改 puzzles.json 数据结构** — 551 局数据保持原样，章节通过 `stars`/`subcategory` 字段映射
2. **老存档零迁移** — 章节解锁状态从 `PuzzleProgress` 推导，不新增存档字段
3. **段位门禁用 enum 封装** — 集中管理，避免散落在各 View 里的硬编码判断
4. **Phase Q1-Q4 闭环，Q5 可选** — 金币经济系统不阻塞主流程

### 1.3 数据现状（设计依据）

对 `puzzles.json` 551 局的实际统计：

| stars | 数量 | subcategory | solutionMode |
|-------|------|-------------|--------------|
| 1★ | 110 | 入门 | 17 freePlay + 93 guided |
| 2★ | 110 | 初级 | 全部 guided |
| 3★ | 110 | 中级 | 全部 guided |
| 4★ | 110 | 高级 | 全部 guided |
| 5★ | 111 | 大师 | 全部 guided |

- 每个难度级别 **恰好 110-111 局**，分布极度均匀
- 17 个 freePlay 残局全部分布在 1★ 入门级（有 solution 但标记 freePlay）
- 全部 551 局 source = "适情雅趣"

## 二、Phase Q1：残局章节制

### 2.1 章节划分策略

#### 方案对比

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A. 按 stars 硬分 | 每个 stars 级别 = 1 章 | 简单 | 5 章，太少；每章 110 局太多 |
| B. 按 subcategory + 数量拆分 | 在 stars 基础上进一步切分 | 灵活 | 需手动指定每局归属 |
| **C. 按 stars 分大章 + 数量拆子章** | 7 章，前 2 章各 50 局，后 5 章各 ~90 局 | ✅ 采用 | — |

**采用方案 C**，与需求文档一致。

> **实现关键**：章节定义放代码里（静态常量），不修改 puzzles.json。ChapterStore 启动时按规则把 551 局分到 7 章。

#### 分章算法：全局排序 + 全局索引切分（P0-1 修正）

⚠️ ** Vera P0-1 修正**：原方案用每章独立筛选候选池 + offset 切片，多章共享同一 stars 区间时会导致重叠或遗漏。修正为**全局排序后用全局起止索引切分**：

**Step 1**：将 551 局按 `(stars, id)` 排序，得到全局有序列表

**Step 2**：各章通过 `globalStart..<globalEnd` 在全局列表中切片

```
全局序列（551局，按 stars 升序 + id 升序）：
位置 0-49   → ch1（50局，1★前半）
位置 50-99  → ch2（50局，1★后半 + 2★开头）
位置 100-179 → ch3（80局，2-3★过渡）
位置 180-279 → ch4（100局，3★中段）
位置 280-379 → ch5（100局，3-4★过渡）
位置 380-479 → ch6（100局，4-5★过渡）
位置 480-550 → ch7（71局，5★末段）
```

每个 puzzle 只属于一个全局位置，**零重叠、零遗漏**。

#### 新增文件：`Models/PuzzleChapter.swift`

```swift
import Foundation

// MARK: - 章节定义（静态配置）

/// 章节解锁条件
/// P0-3 修正：增加 .or case，段位提前解锁放到配置层而非硬编码
enum ChapterUnlockCondition {
    case none                                           // 无前置（第一章）
    case completeChapter(chapterId: String, count: Int) // 通关前一章 N 局
    case rank(Rank)                                     // 达到段位
    case and([ChapterUnlockCondition])                  // 全部满足
    case or([ChapterUnlockCondition])                   // 任一满足（段位提前解锁用）
}

/// 章节通关奖励
enum ChapterReward {
    case unlockChapter(chapterId: String)
    case theme(BoardTheme)
    case title(String)
    case feature(UnlockedFeature)
}

/// 章节静态配置（编译期确定，不入存档）
/// P0-1 修正：用 globalStart/globalEnd 替代 minStars/maxStars/offset
struct ChapterConfig {
    let id: String                    // "ch1"..."ch7"
    let titleKey: String              // L10n key
    let subtitleKey: String           // L10n key
    let globalStart: Int              // 在全局排序列表中的起始索引
    let globalEnd: Int                // 结束索引（exclusive）
    let unlockCondition: ChapterUnlockCondition
    let reward: ChapterReward?

    /// 章节显示编号（1-7）
    var displayNumber: Int {
        Int(id.replacingOccurrences(of: "ch", with: "")) ?? 0
    }
}

// MARK: - 章节运行时数据（从 PuzzleStore 推导）

/// 章节运行时状态（每次打开章节列表时计算，不持久化）
/// P0-2 修正：isUnlocked 改为 var，支持两遍构建
struct PuzzleChapter: Identifiable {
    let id: String
    let config: ChapterConfig
    let puzzles: [Puzzle]              // 本章包含的残局列表
    let completedCount: Int            // 已通关数（从 PuzzleProgress 推导）
    var isUnlocked: Bool               // 是否已解锁（两遍构建中 Pass 2 修改）
    let unlockDescription: String      // 解锁条件描述（未解锁时显示）

    var title: String { L10n.shared.t(config.titleKey) }
    var subtitle: String { L10n.shared.t(config.subtitleKey) }
    var totalCount: Int { puzzles.count }
    var progress: Double {
        totalCount == 0 ? 0 : Double(completedCount) / Double(totalCount)
    }
    var isComplete: Bool {
        completedCount >= totalCount
    }
}
```

#### 设计要点

1. **ChapterConfig 是静态枚举/结构体**，定义在代码里，不读 JSON
2. **PuzzleChapter 是运行时推导数据**，不持久化——每次从 `PuzzleStore.progress` 计算解锁状态和进度
3. **ChapterUnlockCondition 用 enum**，不传闭包（Codable 友好，可测试）

### 2.3 ChapterStore 设计

#### 新增文件：`Services/ChapterStore.swift`

```swift
import Foundation

/// 章节管理器：负责按全局排序把 551 局分配到 7 个章节，并计算解锁状态
/// P0-1 修正：全局排序 + 全局索引切分
/// P0-2 修正：两遍构建，Pass 1 算 puzzles + completedCount，Pass 2 算 isUnlocked
final class ChapterStore {
    static let shared = ChapterStore()

    private(set) var chapters: [PuzzleChapter] = []

    private init() {
        rebuildChapters()
    }

    // MARK: - 全局排序列表

    /// 全局排序后的 puzzle 列表（按 stars 升序 + id 升序）
    private lazy var globalSorted: [Puzzle] = {
        PuzzleStore.shared.puzzles.sorted { a, b in
            if a.stars != b.stars { return a.stars < b.stars }
            return a.id < b.id
        }
    }()

    // MARK: - 两遍构建

    func rebuildChapters() {
        let progress = PuzzleStore.shared.progressMap

        // Pass 1: 构建所有章节的 puzzle 列表 + completedCount（isUnlocked 暂设 false）
        var built: [PuzzleChapter] = ChapterDefinitions.chapters.map { config in
            let puzzles = Array(globalSorted[config.globalStart..<config.globalEnd])
            let completedCount = puzzles.filter { progress[$0.id]?.isCompleted == true }.count
            return PuzzleChapter(
                id: config.id,
                config: config,
                puzzles: puzzles,
                completedCount: completedCount,
                isUnlocked: false,  // Pass 2 填充
                unlockDescription: unlockDescription(for: config.unlockCondition)
            )
        }

        // Pass 2: 根据已构建的 completedCount 计算解锁状态
        let profile = PlayerProfileStore.shared.profile
        for i in built.indices {
            built[i].isUnlocked = checkUnlock(
                built[i].config.unlockCondition,
                profile: profile,
                builtChapters: built
            )
        }
        chapters = built
    }

    // MARK: - 解锁检查

    private func checkUnlock(
        _ condition: ChapterUnlockCondition,
        profile: PlayerProfile,
        builtChapters: [PuzzleChapter]
    ) -> Bool {
        switch condition {
        case .none:
            return true
        case .completeChapter(let chId, let count):
            let chapter = builtChapters.first { $0.id == chId }
            return (chapter?.completedCount ?? 0) >= count
        case .rank(let rank):
            return profile.rank >= rank
        case .and(let conditions):
            return conditions.allSatisfy { checkUnlock($0, profile: profile, builtChapters: builtChapters) }
        case .or(let conditions):
            return conditions.contains { checkUnlock($0, profile: profile, builtChapters: builtChapters) }
        }
    }

    private func unlockDescription(for condition: ChapterUnlockCondition) -> String {
        switch condition {
        case .none:
            return ""
        case .completeChapter(let chId, let count):
            let chapterTitle = ChapterDefinitions.chapters.first { $0.id == chId }?.titleKey ?? chId
            return String(format: L10n.shared.t("chapter.unlock.completePrev"),
                         L10n.shared.t(chapterTitle), count)
        case .rank(let rank):
            return String(format: L10n.shared.t("chapter.unlock.rank"), rank.localizedTitle)
        case .and(let conditions):
            return conditions.map { unlockDescription(for: $0) }.joined(separator: " + ")
        case .or(let conditions):
            // or 条件取任一可满足的描述
            return conditions.map { unlockDescription(for: $0) }.joined(separator: " / ")
        }
    }

    // MARK: - 查询

    func chapter(byId id: String) -> PuzzleChapter? {
        chapters.first { $0.id == id }
    }

    /// 刷新章节状态（残局完成、段位升级后调用）
    /// ⚠️ 见 §九 P2-1 完整 refresh 触发点清单
    func refresh() {
        rebuildChapters()
    }
}
```

```swift
struct ChapterSelectView: View {

            ChapterPuzzleListView(chapter: chapter)

                dismissButton: .default(Text(L10n.shared.t("common.confirm")))
            )
        }
        .onAppear {
            ChapterStore.shared.refresh()
        }
    }
}
```

### 2.6 老存档兼容

**零迁移设计**：

1. 章节是 UI 层概念，`puzzles.json` 不改
2. `PuzzleProgress` 结构不改，已通关的残局进度保留
3. 章节解锁状态通过 `ChapterStore.refresh()` 实时计算：
   - `.completeChapter(chId, count)` → 查 `PuzzleStore.progressMap` 统计该章节范围内的完成数

4. 老用户打开 App → 章节自动从已有进度推导，不会丢失任何通关记录

```swift
/// 可解锁的功能
enum UnlockedFeature: String, Codable, CaseIterable {
    case chapter2Early       // 第二章提前解锁
    case chapter3Early       // 第三章提前解锁
    case freePlayPuzzles     // freePlay 残局全解锁
    case engineAnalysis      // 引擎分析（Phase 2）
    case aiCoach             // AI 教练（Phase 3）
    case openingTreeBrowse   // 开局树浏览
    case openingTreeFavorite // 开局树收藏
    case gameRecordExport    // 棋谱导出
    case customTheme         // 自定义主题
}

extension PlayerProfile {
    /// 检查功能是否已解锁
    func isFeatureUnlocked(_ feature: UnlockedFeature) -> Bool {
        switch feature {
        case .chapter2Early:       return rank >= .scholar
        case .chapter3Early:       return rank >= .juren
        case .freePlayPuzzles:     return rank >= .hanlin
        case .engineAnalysis:      return rank >= .hanlin
        case .aiCoach:             return rank >= .master
        case .openingTreeBrowse:   return rank >= .scholar
        case .openingTreeFavorite: return rank >= .sage
        case .gameRecordExport:    return rank >= .sage
        case .customTheme:         return rank >= .sage
        }
    }
}
```

- 集中在一个 enum 里，避免在各 View 散落 `rank >= .hanlin` 判断

## 四、Phase Q3：成就系统激活

### 4.1 成就→段位联动

#### 修改文件：`Models/Achievement.swift`（AchievementManager）

在 `AchievementManager.unlock()` 中增加段位贡献：

```swift
@discardableResult
func unlock(_ achievementId: String) -> Bool {
    let current = store.profile
    if current.unlockedAchievements.contains(achievementId) { return false }

    _ = store.update { profile in
        if !profile.unlockedAchievements.contains(achievementId) {
            profile.unlockedAchievements.append(achievementId)
        }
        // Q3 新增：成就贡献段位
        // tutorial_done → 等价 1 个胜场
        // first_puzzle → 等价 1 个残局通关
    }

    // 触发段位检查
    if let newRank = store.profile.checkRankUp() {
        store.update { $0.rank = newRank }
        // TODO: 发送段位升级通知
    }

    return true
}
```

**注意**：成就贡献的胜场/残局数不能重复计入 `totalWins`/`puzzlesCompleted`，否则会双重计算。建议用单独的 `bonusWins`/`bonusPuzzles` 字段，或直接在 `checkRankUp` 里检查特殊成就。

**推荐方案**：不改 `totalWins`/`puzzlesCompleted`，而是在 `checkRankUp()` 里额外考虑成就加成：

```swift
func checkRankUp() -> Rank? {
    var bestRank = rank
    let effectiveWins = totalWins + achievementBonusWins
    let effectivePuzzles = puzzlesCompleted + achievementBonusPuzzles

    for candidate in Rank.allCases {
        if candidate > bestRank
            && effectiveWins >= candidate.requiredWins
            && effectivePuzzles >= candidate.requiredPuzzles {
            bestRank = candidate
        }
    }
    return bestRank > rank ? bestRank : nil
}

private var achievementBonusWins: Int {
    unlockedAchievements.contains("tutorial_done") ? 1 : 0
}
private var achievementBonusPuzzles: Int {
    unlockedAchievements.contains("first_puzzle") ? 1 : 0
}
```

### 4.2 新增行为型成就

替换 8 个纯统计型成就为行为型成就。**关键约束**：已解锁的旧成就不回收。

**迁移策略**：
1. 保留旧成就 ID 在 `unlockedAchievements` 中（已解锁的老用户不受影响）
2. 新增 8 个新 ID（如 `kill_mate_horse_cannon`、`kill_mate_double_rook` 等）
3. 旧 ID 从 `AchievementLibrary` 中移除定义，但保留在已解锁用户的记录中
4. 成就总数从 34 变为 34（-8 旧 +8 新）

**需要 GameViewModel 配合**：对弈结束时检测特殊杀法类型。这部分属于实现层面，方案只定义触发条件。

## 六、Phase Q5：金币经济系统（可选）

### 6.1 数据模型

#### 新增文件：`Models/PlayerWallet.swift`

```swift
import Foundation

/// 玩家钱包
struct PlayerWallet: Codable {
    var coins: Int = 0
    var lifetimeEarned: Int = 0       // 累计获得（不减少）
    var spentAt: [String: Int] = [:]  // 商品 ID → 已花费总额

    // Codable 向后兼容
    enum CodingKeys: String, CodingKey {
        case coins, lifetimeEarned, spentAt
    }
    init() {}
    init(from decoder: Decoder) throws {
        let c = try decoder.container(keyedBy: CodingKeys.self)
        coins = try c.decodeIfPresent(Int.self, forKey: .coins) ?? 0
        lifetimeEarned = try c.decodeIfPresent(Int.self, forKey: .lifetimeEarned) ?? 0
        spentAt = try c.decodeIfPresent([String: Int].self, forKey: .spentAt) ?? [:]
    }
}

/// 金币商店商品
enum ShopItem: String, CaseIterable {
    case extraHint          // 额外提示×1
    case unlockPuzzleEarly  // 3★残局提前访问
    case blitzTimeBonus     // 闪电局时间+1分钟
    case undoinDailyChallenge // 每日挑战悔棋
    case pieceStyle         // 专属棋子样式
    case customTheme        // 自定义棋盘主题

    var price: Int {
        switch self {
        case .extraHint:            return 10
        case .unlockPuzzleEarly:    return 20
        case .blitzTimeBonus:       return 15
        case .undoinDailyChallenge: return 30
        case .pieceStyle:           return 100
        case .customTheme:          return 200
        }
    }

    var nameKey: String { "shop.\(rawValue).name" }
    var descKey: String { "shop.\(rawValue).desc" }
}

/// 钱包存储
final class WalletStore {
    static let shared = WalletStore()
    private let key = "chinesechess.playerWallet"

    var wallet: PlayerWallet {
        guard let data = UserDefaults.standard.data(forKey: key),
              let decoded = try? JSONDecoder().decode(PlayerWallet.self, from: data) else {
            return PlayerWallet()
        }
        return decoded
    }

    func save(_ wallet: PlayerWallet) {
        guard let data = try? JSONEncoder().encode(wallet) else { return }
        UserDefaults.standard.set(data, forKey: key)
    }

    @discardableResult
    func earn(_ amount: Int, reason: String) -> PlayerWallet {
        var w = wallet
        w.coins += amount
        w.lifetimeEarned += amount
        save(w)
        return w
    }

    @discardableResult
    func spend(_ item: ShopItem) -> Bool {
        var w = wallet
        guard w.coins >= item.price else { return false }
        w.coins -= item.price
        w.spentAt[item.rawValue, default: 0] += item.price
        save(w)
        return true
    }
}
```

## 十一、设计决策记录

### D1: 为什么不修改 puzzles.json？

章节制是 UI 层和导航层的重组，不是数据层的变更。修改 puzzles.json 会：
- 增加数据迁移风险（老用户存档兼容）
- 增加 JSON 体积（加章节字段 × 551 局）
- 与版本管理耦合（章节配置变化要改 JSON）

**选择**：章节配置在代码里（`ChapterDefinitions`），运行时从 `stars`/`id` 推导。

### D2: 为什么 PuzzleChapter 不持久化？

章节状态（解锁/进度）完全可以从 `PuzzleProgress` + `PlayerProfile` 推导。持久化会：
- 增加存档复杂度
- 引入数据不一致风险（如果玩家手动改存档）

**选择**：`PuzzleChapter` 是运行时计算结果，每次打开章节列表时 `ChapterStore.refresh()`。

### D3: 为什么段位解锁用 enum 而不是字典？

`UnlockedFeature` enum 的优点：
- 编译期检查完整性（漏加 case 会编译报错）
- 可穷举测试
- 类型安全

字典方案（`["engineAnalysis": true]`）容易漏 key、拼写错误。

### D4: 为什么 Q5 金币系统推荐推迟？

Q5 对 Q1-Q4 的侵入性分散在 10+ 个文件中。如果 Q5 设计不完善就上线，会导致：
- 各模块耦合金币检查逻辑
- Q1-Q4 的测试需要 mock 金币系统
- 金币经济平衡需要用户测试数据（当前没有）

**选择**：Q5 推迟到 v3.7.0，Q1-Q4 不预留金币钩子。金币系统独立性高，后加侵入性可控。

#### P1-7: 大师挑战统计规则

**明确规则**：
- `isMasterChallenge` 在 `GameViewModel.init` 时传入，生命周期 = 单局，不可恢复
- 胜场计入 `totalWins`（正常升级），负场**不计** `totalLosses`（鼓励尝试）
- 原因：大师挑战是高风险高回报的模式，如果胜负都计，玩家会因为害怕掉胜率而不玩
- 胜率虚高问题可接受——大师挑战只占每日挑战的一个模式位，不会大量刷

实现方式：
```swift
struct GameViewModel {
    let isMasterChallenge: Bool  // init 时传入，默认 false

    func recordResult(_ result: GameResult) {
        switch result {
        case .win:
            // 正常记录胜场
        case .lose:
            if !isMasterChallenge {
                // 正常记录负场
            }
            // isMasterChallenge 时跳过
        case .draw:
            // 正常记录
        }
    }
}
```
