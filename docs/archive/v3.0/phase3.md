# Phase 3：Route A — 评估函数深度调优

> 路线：**Route A**（自研引擎提升路径）
> 周次：Week 3-4
> 依赖：Phase 2 搜索算法升级完成（评估改进需要在新搜索框架上验证）

---

## 目标

在搜索优化基础上，通过评估函数的系统性改进，将自研引擎棋力推向 Elo ~2200-2500。这是自研手写评估的"最后一波大规模投入"——如果 Route A Pikafish 可行，后续不再深耕手写评估。

---

## 具体实施内容

### 3.1 位置权重表全面重写

**当前问题**：horse/chariot/cannon 表格大量 0 值或 2-8 的微值，位置评估几乎无效。

**改进内容**：
- 逐一审视每种棋子的位置权重表
- 参考象棋理论中的位置价值（如车占肋道、马跳卧槽、炮镇中路）
- 增加位置特定性：同一棋子在不同阶段（开局/中局/残局）的权重差异
- 可能引入残局阶段检测（剩余子力 ≤ 阈值），切换残局权重表

**数据来源**：象棋教科书公开知识 + Pikafish 评估差异分析（用 Pikafish 分析当前引擎的局面判断错误，反向推导权重问题）

### 3.2 棋型识别扩展（8 → 30+ 种）

**当前实现**：`PatternRecognizer` 仅 8 种棋型，判定简化。

**扩展清单**：

| 分类 | 棋型 | 判定要点 |
|------|------|---------|
| **攻击型** | 钓鱼马 | 马在特定位置 + 控制将位 + 有支撑 |
| | 卧槽马 | 马在对方将台 + 无法被驱赶 |
| | 拐角马 | 马在对方拐角 + 配合攻击 |
| | 担子炮 | 两炮同线 + 中间无子或有一个间隔子 |
| | 巡河炮 | 炮在己方河沿 + 控制河界 |
| | 当头炮 | 炮在中路 + 直接威胁将 |
| | 叠炮 | 两炮同线叠放 |
| **防守型** | 羊角士 | 士在特定位置形成防御 |
| | 飞相局 | 相展开形成防御结构 |
| | 高车保河 | 车在高位保护河界 |
| **兵卒型** | 过河兵 | 兵已过河 + 威胁增加 |
| | 兵线协同 | 多兵同线推进 |
| | 兵阵结构 | 兵阵完整不散乱 |
| **将帅型** | 飞将威胁 | 将帅对面（无遮挡）威胁 |
| | 防空评估 | 将的上空无防守子力 |
| | 九宫安全 | 九宫内防守子力充足度 |
| **子力协同** | 车炮配合 | 车炮同线形成威胁 |
| | 马炮配合 | 马炮配合攻击特定位置 |
| | 双车联动 | 两车同线或交叉控制 |
| | 双马连环 | 双马互保 |
| **特殊** | 先手价值 | 量化走法先手属性 |
| | 牵制 | 子力被牵制无法移动 |
| | 闪击 | 移动一个子暴露攻击 |
| | 堵塞 | 关键格被堵 |
| | 过载 | 防守子力承担过多防守任务 |

**实现方式**：每种棋型在 `PatternRecognizer` 中添加独立的识别函数，返回棋型加/减分。

### 3.3 机动性评估重写

**当前实现**：车数空格数，马数跳点，过于简化。

**改进内容**：

| 棋子 | 当前 | 改进后 |
|------|------|--------|
| 车 | 数空格数 | 区分有价值方向（控制中线、肋道加倍）+ 活跃度（是否攻击对方半区） |
| 马 | 数跳点 | 区分好马（有根、不蹩脚、活跃位置）和坏马（边角、蹩脚、无根） |
| 炮 | 无机动性评估 | 评估炮架质量（有炮架 vs 无炮架）+ 控制线路 |
| 兵 | 无机动性 | 过河兵机动性（可横走）+ 未过河兵推进价值 |

### 3.4 兵卒评估细化

- 过河兵：价值提升（接近将位 → 分数递增）
- 兵路线协同：同列多兵协同推进加分
- 兵阵结构：散乱兵阵减分，紧凑兵阵加分
- 残局兵卒价值：残局阶段兵卒权重提升（残局中兵可决定胜负）

### 3.5 将帅安全增强

- 飞将威胁评估：检测将帅对面情况
- 防空评估：将上空防守子力检测
- 九宫安全评分：综合士/象/将位置的防守强度
- 不同阶段的将帅安全：开局中侧重进攻，残局侧重将的活跃度

### 3.6 子力协同评估

- 车炮配合：同线车炮加分
- 马炮配合：马炮联合攻击加分
- 双子联动：多子协同控制关键格
- 协同减分：子力相互阻碍（如马塞象眼）

### 3.7 权重系统化校准方法论

30+ 种棋型各有独立权重值，手工逐个调参会导致相互冲突。采用以下系统化方法：

**初始值来源**：
- 象棋教科书公开知识中的相对价值关系（如"卧槽马优于钓鱼马"）
- Pikafish 差异分析：用 Pikafish 分析当前引擎的局面判断错误，反向推导权重问题
- 现有引擎的权重值作为基准线

**迭代调整流程**：
1. 设定初始权重 → 自对弈 100 局验证
2. 记录每局的评估错误（与 Pikafish 评估对比）→ 识别系统性偏差
3. 调整偏差最大的 3-5 个权重 → 再次自对弈验证
4. 重复 3-4 轮迭代

**自动化参数搜索（推荐）**：
- 采用 SPSA（Simultaneous Perturbation Stochastic Approximation）或 CoEA（Covariance Matrix Adaptation）自动搜索
- 原理：对多个参数同时施加随机扰动，通过胜率变化估计梯度方向
- 每轮：随机扰动权重 → 自对弈 N 局 → 计算胜率变化 → 更新权重
- 预计 20-50 轮迭代可收敛
- 此方法不需要 GPU，CPU 自对弈即可

**冲突检测**：
- 每轮调整后，检查是否有权重值出现不合理比例（如棋型加分 > 子力值）
- 设置权重上下限：棋型加分不超过子力值的 30%

**验收标准**：
- 权重集经过至少 3 轮自对弈验证，无系统性偏差
- 评估速度基准：每次 `evaluate()` ≤ 50μs（详见 3.8 性能基准）

### 3.8 评估函数性能基准

评估函数是搜索的热点路径，棋型从 8 种扩展到 30+ 种可能影响搜索速度。

**性能要求**：
- 每次 `evaluate()` 调用 ≤ 50μs（M1 基准）
- 搜索整体速度下降不超过 20%（相比 Phase 2 的搜索速度）

**回退策略**：
- 如果性能下降超过 20%，优先精简棋型识别（合并相似棋型、简化判定逻辑）
- 关键路径优化：棋型识别改为位运算或查表
- 极端情况：保持 15-20 种核心棋型，其余作为"增强包"在非搜索路径（如复盘分析）中使用

Phase 3 完成后，启动外部基准验证：
- xiangqi.com 排位赛：至少 50 局（详见验证标准中的统计学要求）
- 与已知 Elo 的引擎交叉对弈：作为主要验证方式（详见下方）
- 记录对局用于后续分析
