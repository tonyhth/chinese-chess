## 一、当前能力盘点

### 1.1 AI 引擎现状

| 维度 | 当前实现 | 行业水平 | 差距 |
|------|---------|---------|------|
| 搜索算法 | Negamax + Alpha-Beta + IDS | PVS/NegaScout + IDS | 缺少 Principal Variation Search，根节点效率可提升 10-15% |
| 评估函数 | 手写子力+位置+棋型+将帅安全+机动性 | NNUE 神经网络 | **质的差距**——Pikafish NNUE Elo 3954，手写评估实际约 1500-1800（详见 1.4） |
| 走法排序 | TT最佳 > 将军 > MVV-LVA > Killer > 威胁 > 历史 | TT > Countermove > History + LMR 调优 | 缺少 Countermove Heuristic，LMR 仅基础实现 |
| 置换表 | 固定数组，深度优先替换 | 多桶替换（depth-prefer + age） | 替换策略偏简单，长对局 TT 命中率下降 |
| 开局库 | 4602 位置 / 7022 走法 / 加权随机 | 专业开局库 10万+ 位置 | 量级差距（约 20x），覆盖面不足 |
| 残局库 | 20 种规则匹配（≤6 子） | Nalimov/Sygman 完整残局数据库 | 规则匹配 vs 精确解——无法处理非典型残局 |
| 杀法搜索 | 连将杀 DFS，深度 12-16，8 走法剪枝 | 专业级深度 30+ | 剪枝有假阳性风险，深度不够 |
| Quiescence | 吃子 QS，深度 4-6 | 吃子+将军 QS | 缺少将军延伸 QS |

**结论**：引擎在"手写评估 + Alpha-Beta"范式中做出了基础实现，但**实际棋力远低于此前预估**。

### 1.4 【v4.0 新增】AI 棋力真实基线评估

**事实**：洪涛实际棋力不到业余段位，但能轻松战胜当前大师级 AI。

**推断**：当前大师级 AI 实际 Elo 约 **1500-1800**，而非此前方案中估计的 ~2600。高估幅度约 800-1100 分。

**代码层面的根因分析**：

| 问题 | 代码证据 | 影响 |
|------|---------|------|
| 评估函数权重值过小 | 位置权重表数值 0-40（子力值 100-10000），位置评估几乎被子力评估淹没 | 评估精度低，搜索无法区分细微局面差异 |
| 位置权重表粒度粗糙 | horse/chariot/cannon 表格大量 0 值或 2-8 的小值 | 位置引导几乎无效 |
| 棋型识别覆盖面窄 | 仅 8 种棋型，判定逻辑简化（如钓鱼马只看距离，不验证控制） | 战术意识薄弱 |
| 机动性评估过于简化 | 车只是数空格数，马只数跳点 | 无法反映真实子力活跃度 |
| 无 PVS | rootSearch 对所有走法用全窗口搜索 | 搜索效率低，同时间内搜索深度比 PVS 少 1-2 层 |
| QS 不搜将军 | quiescenceSearch 只搜索吃子走法 | 地平线效应严重，忽略将军续着 |
| 开局库加权随机（大师级） | masterSearch 用 lookupWeightedRandom | 大师级开局不选最优，人为降低棋力 |
| 搜索深度不足 | 大师级 baseDepth 7-8，IDS 受时间限制可能提前终止 | 在复杂中局局面无法看到足够深度 |

**这意味着**：从当前 ~1800 到目标 Elo 3500+，需要跨越约 **1700 分**。这不是调参能做到的——需要评估函数范式转变（NNUE）+ 搜索算法全面升级。

**首要任务**：v3.0 Week 1 必须运行自对弈框架，测出当前真实 Elo 基线。所有后续提升的量化都基于这个基线。

## 三、AI 棋力升级方案

### 3.1 核心目标：Elo 3500+（P0 中的 P0）

**这是核心目标。** v3.1 通过 Pikafish 集成实现 AI 棋力达到 Elo 3500+。如果首次集成后未达目标，接受 3200+ 作为阶段性交付，后续持续调优。

**优先级声明**：AI 棋力提升是 v3.0 的第一优先级，超越所有其他功能。可玩性再好，棋力不行用户也留不住。所有其他工作服务于或等待 AI 棋力提升。

### 3.2 技术路线：Route A 单路线（Pikafish 集成）

```
                  ┌── Route A：Pikafish 集成 ──→ Elo 3500-3954
                  │   (v3.1 主路线)
Elo 3500+ 目标 ──┤
                  │   (v3.2+ 远期备选，当前条件不具备)
                  └── Route B：自研 NNUE ──→ Elo 3500+
```

**【v6.0 决策】Route B 推迟原因**：
- 自研 NNUE 需要 GPU 训练资源（RTX 3090/4090 或云 GPU），当前无可用资源
- 需 ML/C++ 方面的外部人力（训练流水线 + clean-room 推理引擎），当前团队不具备
- 工期 12-16 周，风险高，与现有团队资源不匹配
- Route A（Pikafish 集成）是最快达到 3500+ 的路径，优先争取

**决策点**：v3.0 Week 2 结束时，基于以下两个评估结果确认 Route A 可行性：
1. GPLv3 + App Store 法律合规评估
2. Pikafish C++ iOS 编译 + C 接口暴露 Spike 结果

**Route A 不可行时的兜底方案**（详见 3.5 节）。

### 3.3 Route A：Pikafish 集成

#### 技术架构

```
┌─────────────────────────────────────────────┐
│                 AIEngine                     │
│  ┌────────────────┐  ┌────────────────────┐ │
│  │  NativeEngine   │  │  PikafishBridge    │ │
│  │  (自研引擎)      │  │  (C++ interop)     │ │
│  │  depth 1-10     │  │  Direct C++ call   │ │
│  │  手写评估        │  │  NNUE 评估         │ │
│  └────────────────┘  └────────────────────┘ │
│         ↑                    ↑               │
│    beginner~medium      hard~master          │
│    快速模式             大师模式              │
└─────────────────────────────────────────────┘
```

#### iOS 集成方案

iOS 不支持 `Process` API（沙箱禁止创建外部进程），UCI stdin/stdout 通信不可行。正确方案：

1. **macOS**：`Process` + UCI 协议（可行）
2. **iOS**：Pikafish 核心搜索编译为 C 静态库，通过 C header 桥接直接调用搜索函数

**C 接口设计草案**：
```c
// pikafish_capi.h
typedef struct PFPosition PFPosition;
typedef struct PFSearchLimits {
    int depth;
    int movetime_ms;
    int nodes;
} PFSearchLimits;

PFPosition* pf_position_from_fen(const char* fen);
void pf_position_destroy(PFPosition* pos);
char* pf_search_bestmove(PFPosition* pos, PFSearchLimits limits);
void pf_free_string(char* s);
```

#### GPLv3 合规评估

v3.0 Week 1-2 期间完成法律评估：
- GPLv3 要求分发 GPL 代码时必须提供完整源码
- App Store 的 DRM 签名与 GPLv3 "no further restrictions" 存在冲突
- 可能的合规路径：
  1. App 本身开源（MIT/GPL 双许可）
  2. Pikafish 作为独立可下载组件（不嵌入 Bundle）
  3. 与 Pikafish 作者协商
- **如果法律评估结论为不合规，启动兜底方案（详见 3.5）**

### 3.4 搜索算法全面升级（v3.0 Phase 1）

无论 Route A 是否可行，自研引擎的搜索优化都是必须的——它是 Route A 的技术基础（低难度引擎），也是兜底方案的核心。

| 优化项 | 实现要点 | 预期效果 |
|--------|---------|---------|
| PVS | 第一个走法全窗口，后续零窗口 | 搜索效率 +10-15% |
| LMR（Late Move Reductions） | 走法排序靠后的走法减少搜索深度 | 节点数减少 30-50% |
| Countermove Heuristic | 记录上一步产生 cutoff 的走法 | 排序质量提升 |
| Null Move Pruning | 跳过一步后如果仍然 β cutoff 则剪枝 | 搜索节点数减少 20-30% |
| Futility Pruning | 浅层评估远低于 α 时跳过 | 额外剪枝 |
| Razoring | 浅层评估远低于 α 时做 QS 验证 | 前置剪枝 |
| TT 多桶替换 | depth-prefer + age 双桶策略 | TT 命中率提升 |
| 将军延伸 QS | QS 中搜索将军走法 | 地平线效应减少 |
| Internal Iterative Deepening | TT 无最佳走法时先浅搜 | 排序质量提升 |

### 3.5 Route A 不可行时的兜底方案

**这是 v6.0 新增的关键章节。** 如果 Pikafish GPLv3 不合规且无合规路径，或 iOS C++ interop 不可行，v3.1 需要替代方案。

#### 兜底方案 1：评估函数深度调优（自研引擎极限提升）

**思路**：在搜索优化（Elo ~2200）的基础上，通过评估函数的系统性改进，尽可能逼近 Elo 2800-3000。

**具体措施**：
- 位置权重表全面重写：放大 10-20 倍，增加位置特定性（每格独立权重）
- 棋型识别扩展：从 8 种扩展到 30+ 种，增加判定精度
- 机动性评估重写：车/马/炮的活跃度建模，考虑控制和威胁
- 兵卒评估细化：过河兵增强、兵路线协同、兵阵结构
- 将帅安全增强：飞将威胁评估、防空评估
- 子力协同：车炮配合、马炮配合、双子联动
- Temp 评估：先手价值量化

**预估上限**：手写评估 + 搜索优化的天花板约 Elo 2800-3000。**无法达到 3500+**——这是手写评估的物理极限。

**适用场景**：作为 v3.1 的最低保底——即使只有 2800，也比当前 ~1800 有质的飞跃。

#### 兜底方案 2：轻量 NNUE（外包/协作）

**思路**：如果 Route B 的核心障碍是"团队没有 ML/C++ 能力"，可以通过外包/协作解决。

**方案**：
- 聘请 NNUE 训练顾问（兼职/项目制）：负责训练流水线搭建和首版模型训练
- C++ 推理引擎外包：基于 NNUE 论文 clean-room 实现，C header 接口交付
- Cody 负责集成：Swift 桥接层 + 搜索集成

**关键前提**：需要 GPU 资源 + 外部人力预算。如果洪涛批准，可在 Route A 失败后立即启动。

**工期**：12-16 周（与原 Route B 相同）

#### 兜底方案 3：Pikafish 非嵌入方案

**思路**：如果 GPLv3 与 App Store 嵌入式分发不兼容，考虑非嵌入方案。

**方案**：
- App 不内置 Pikafish 二进制
- 用户自行下载 Pikafish 开源版本
- App 通过本地 UCI 协议（macOS Process）或文件交换与 Pikafish 通信
- macOS 版本可率先支持

**限制**：
- iOS 无法使用（沙箱限制）
- 用户体验差（需要用户手动安装）
- 不适合大众用户

**适用场景**：作为 macOS 版的高级功能，配合兜底方案 1 覆盖 iOS。

#### 兜底方案选择决策树

```
Route A 法律评估结果
├── 合规 → Route A（Pikafish 集成）→ v3.1 目标 3500+
└── 不合规
    ├── iOS C++ 可行但法律不合规
    │   ├── macOS：兜底方案 3（非嵌入 Pikafish）
    │   ├── iOS：兜底方案 1（自研极限提升）→ v3.1 目标 2800-3000
    │   └── 远期：兜底方案 2（轻量 NNUE 外包）→ v3.2+ 目标 3500+
    └── iOS C++ 也不可行
        ├── 兜底方案 1（自研极限提升）→ v3.1 目标 2800-3000
        └── 远期：兜底方案 2（轻量 NNUE 外包）→ v3.2+ 目标 3500+
```

**v6.0 明确声明**：如果 Route A 不可行且兜底方案 1 是唯一选择，v3.1 交付标准降为 Elo 2800-3000。这不是理想结果，但仍然是当前 ~1800 的巨大提升。3500+ 目标推迟到 v3.2+（需要 GPU + 外部人力）。

## 四、可玩性提升方案

### 4.1 段位/等级系统

**设计原则**：象棋文化融合 + 可达成感 + 段位特权有实质感

```
段位体系：
─────────────────────────────────────────
学童 ──→ 秀才 ──→ 举人 ──→ 进士 ──→ 翰林 ──→ 国手 ──→ 棋圣
─────────────────────────────────────────

升级条件（累计制，不做赛季重置）：
学童：初始
秀才：在初级获胜 3 局，或通关 10 局残局
举人：在中级获胜 3 局，或通关 30 局残局
进士：在高级获胜 3 局，或通关 60 局残局
翰林：在大师获胜 1 局，或通关 100 局残局
国手：在大师获胜 10 局
棋圣：在大师（Pikafish 全力模式）获胜 3 局

保级机制：无（累计制不降级，避免挫败感）
```

**段位特权——装饰性 + 玩法层面双轨**：

段位特权不只是皮肤/装饰，更要有玩法层面的实质感：


### 4.5 创新玩法（竞品没有）

#### 玩法 1："AI 教练"模式

**核心理念**：不是让 AI 碾压你，而是让 AI 教你。

```
工作方式：
1. AI 根据玩家段位自动调整棋力（比玩家略强）
2. 关键局面（如漏杀、送子）时暂停，弹出提示：
   "这一步有更好的选择，要看看吗？"
3. 玩家可以选择：
   - "提示"：高亮最佳走法的起点
   - "详解"：AI 用 2-3 句话解释为什么这步更好
   - "跳过"：继续对局
4. 对局结束后，AI 生成"本局复盘卡片"：
   - 你走了 X 步好棋，Y 步疑问手
   - 最大失误：第 N 步，应该走...
   - 棋力评分：★★★☆☆
   - 提升建议："你的中局防守偏弱，推荐练习 X 类残局"

技术实现：
- 利用引擎为每步走法评分
- "教练难度" = 玩家当前段位对应难度 + 1
- 关键局面检测：评估分数落差 ≥ 200 分 = 关键局面
```

**讲解生成方案（8 类场景模板）**：

| 场景 | 触发条件 | 讲解模板 | 示例 |
|------|---------|---------|------|
| 送子 | 评估落差 ≥ 300，丢子 | "这步会丢掉{piece}，{better}可以保住它" | "这步会丢掉马，车八进二可以保住它" |
| 漏杀 | 对方有杀棋未防 | "对方有{N}步杀，{better}可以防守" | "对方有3步杀，士五退四可以防守" |
| 错失杀机 | 玩家有杀棋未走 | "这里可以{N}步将杀，{better}是关键" | "这里可以3步将杀，马八进七是关键" |
| 将军机会 | 有将军未走 | "可以将军！{better}先手占优" | "可以将军！炮八平五先手占优" |
| 吃子机会 | 有安全吃子未走 | "可以安全吃掉{piece}，{better}" | "可以安全吃掉对方炮，车二进七" |
| 兵力展开 | 走法未展开子力 | "此时展开子力更重要，{better}" | "此时展开子力更重要，马八进七" |
| 防守优先 | 应防守时进攻 | "当前应先防守，{better}更稳妥" | "当前应先防守，象七退五更稳妥" |
| 控制中线 | 中线控制更优 | "控制中线是关键，{better}" | "控制中线是关键，炮八平五" |

**未匹配场景 fallback**："这步有更好的选择，{better_move}评估高出{delta}分"

**这是我们的核心差异化**——竞品要么太弱要么太强，没有"刚好比你强一点且愿意教你"的中间态。

```swift
enum MoveQuality: Int {
```

## 十、总结

v3.0 的核心目标是让产品从"能玩的象棋工具"进化为"想一直玩的象棋游戏"，最终 AI 棋力达到 Elo 3500+。

**路线策略**（v6.0 修订）：

v3.1 **聚焦 Route A 单路线**（Pikafish 集成）。Route B（自研 NNUE）推迟至远期，原因是 GPU 训练资源 + ML/C++ 外部人力当前不具备。Route A 是最快达到 3500+ 的路径，优先争取。

**三大支柱**：
1. **【P0-绝对优先】AI 棋力质变**：Elo ~1800 → 3500+。v3.0 搜索优化到 ~2200，v3.1 Pikafish 集成到 3500+
2. **【P1-Phase 2 并行】留存机制闭环**：段位（实质特权）+ 成就（34 个）+ 每日挑战（10 种模式）+ AI 教练（8 类讲解）
3. **【P1-差异化创新】AI 教练模式**："刚好比你强一点且愿意教你"——但前提是底层 AI 棋力足够强

**不做的事**（避免过度设计）：
- 不做在线对战（v3.2+）
- 不做浅色模式
- 不做 Apple Watch
- 不做自研 NNUE（v3.2+ 远期）
- 不做"轻量网络残差修正"——要么上 Pikafish，要么自研极限提升

**最关键的三个判断**：
1. **真实 Elo 基线**（Week 1）：自对弈框架必须先测出当前大师级 AI 的真实水平。所有后续提升的量化都基于此
2. **Route A 可行性**（Week 2）：法律评估 + iOS C++ Spike。这是 v3.1 能否按计划推进的关键——如果 Route A 不可行，需要启动兜底方案
3. **兜底方案的天花板**：如果 Route A 不可行，自研极限提升只能到 ~2800-3000。这不是理想结果，但仍然是当前 ~1800 的巨大提升。3500+ 目标需要 Route B（自研 NNUE），但这需要 GPU + 外部人力

## 附录 A：Route B 远期备选（自研 NNUE）

**状态**：推迟至 v3.2+，当前条件不具备

**推迟原因**：
- 需要 GPU 训练资源（RTX 3090/4090 或云 GPU），当前无可用资源
- 需要 ML/C++ 方面的外部人力（训练流水线 + clean-room 推理引擎），当前团队不具备
- 工期 12-16 周，风险高

**技术路径概述**（供远期参考）：

1. **数据生成**：用 Pikafish 自对弈生成 200-500 万局训练数据（使用软件 ≠ 分发软件，不违反 GPL）。8 核并行 7-10 天
2. **训练**：nnue-pytorch 适配象棋（halfKP-xiangqi 特征集，226,800 维），GPU 训练 2-4 天/轮，3-5 轮迭代
3. **推理集成**：clean-room C++ 推理引擎（仅根据 NNUE 论文编写，不参考 GPL 源码），Swift 桥接，copy-make accumulator 策略
4. **法律合规**：训练数据不违反 GPL；推理代码必须 clean-room 实现；训练框架仅在内部使用不分发

**Elo 预估**：
- v1 模型：Elo 3000-3300（保守）
- v2 模型：Elo 3300-3500
- v3+ 模型：Elo 3500+

**启动前提**：
- GPU 资源到位（云 GPU 或本地 GPU）
- ML/C++ 外部人力到位（至少兼职）
- Route A 已确认不可行，或需要 Route B 作为补充
