## 三、各 Phase 详细设计

### Phase 1：并发安全 + 模块边界

**目标：** 消除 C 层并发竞争，恢复单向依赖架构。

#### #1 PositionAnalyzer 统一到 EmbeddedPikafishEngine 调用入口（P0, D2）

**现状分析：**

PositionAnalyzer（actor）通过 `withCheckedContinuation` + `DispatchQueue.global()` 跳出 actor 隔离，直接调用 C API（`pikafish_eval`、`pikafish_multi_pv`）。同时 EmbeddedPikafishEngine 也通过相同模式调用 C API（`pikafish_best_move`）。两者完全并发进入 C 层全局单例 `g_engine`，actor 隔离形同虚设。

**已知风险：**
- Use-After-Free（C 层非线程安全）
- 搜索结果错乱（两个搜索交错污染引擎状态）
- Known Issues 中记录的 `pikafish_quit/init` 循环 bug（测试环境更严重）

**修复方案（统一入口 + 串行队列）：**

> **v2 修订（P0-1 + P0-2）：** 原方案在实例关系和并发保护上存在矛盾。修订要点：
> 1. PositionAnalyzer 必须通过 EngineRouter.shared 获取**共享** EmbeddedPikafishEngine 实例（P0-1）
> 2. activeSearchCount 纯计数器**不能**防止 C 层并发，需引入串行队列替代 DispatchQueue.global()（P0-2）

**P0-1 修正：实例关系**

C 层 `g_engine` 是全局单例，两个 EmbeddedPikafishEngine 实例的 `activeSearchCount` 各算各的，互不知晓。PositionAnalyzer 持有独立实例时，该实例认为安全，但 EngineRouter 管理的实例可能正在执行——两个线程同时进入 C 层，并发竞争未修复。

**结论：PositionAnalyzer 必须通过 EngineRouter.shared 获取共享实例。**

**P0-2 修正：并发串行化**

原方案声称 actor 串行化 + activeSearchCount 保护并发。Vera 指出 actor 锁在 `withCheckedContinuation` suspend 点释放，第二个 async 方法可同时 dispatch 到全局队列进入 C 层。**Vera 是对的。**

当前 `activeSearchCount` 是纯计数器（`+= 1` / `-= 1`），只用于 shutdown 等待，**不阻止并发搜索**。

**修复：将 `DispatchQueue.global()` 替换为串行 `DispatchQueue`：**

```swift
actor EmbeddedPikafishEngine: ChessEngine {
    // C API 调用专用串行队列——保证同一时间只有一个线程进入 C 层
    private let cApiQueue = DispatchQueue(label: "com.chinesechess.pikafish.capi")

    func bestMove(...) async -> String? {
        guard isReady else { return nil }
        activeSearchCount += 1
        defer { activeSearchCount -= 1 }

        return await withCheckedContinuation { continuation in
            cApiQueue.async {  // ← 原 DispatchQueue.global() 改为 cApiQueue
                var buffer = [CChar](repeating: 0, count: 64)
                let result = pikafish_best_move(...)
                continuation.resume(returning: ...)
            }
        }
    }

    // 新增方法，同样用 cApiQueue
    func evaluate(fen: String, moveHistory: [String], depth: Int, timeMs: Int) async -> AnalysisLine? {
        guard isReady else { return nil }
        activeSearchCount += 1
        defer { activeSearchCount -= 1 }

        return await withCheckedContinuation { continuation in
            cApiQueue.async {
                let result = UnsafeMutablePointer<PikafishEvalResult>.allocate(capacity: 1)
                // ... C API 调用，用结构体字段访问替代硬编码偏移量
                continuation.resume(returning: ...)
            }
        }
    }

    func multiPV(fen: String, moveHistory: [String], count: Int, depth: Int, timeMs: Int) async -> [AnalysisLine] {
        // 同理，用 cApiQueue
    }
}
```

**串行队列如何解决 P0-2：**

| 问题 | 串行队列如何解决 |
|------|-----------------|
| actor suspend 点释放锁，两个方法并发进入 C 层 | `cApiQueue` 是 serial queue，即使两个闭包同时提交，GCD 也只执行一个，另一个排队等待 |
| activeSearchCount 不阻止并发搜索 | 串行队列物理上阻止并发，activeSearchCount 继续用于 shutdown 等待 |
| bestMove 和 evaluate 排队 | **期望行为**——C 层全局单例本就不支持并发 |

**P1-6 补充：C API struct 布局兼容性**

已核对 `pikafish_api.h`：
- `pikafish_best_move`：输出通过 `char* buffer` 参数，只返回 UCI 走法
- `pikafish_eval` / `pikafish_multi_pv`：输出通过 `PikafishEvalResult*`（score_cp + depth + best_move[16] + pv[256]）

两者是**不同的返回类型**，不存在偏移量复用。PositionAnalyzer 当前的硬编码偏移量（`advanced(by: 8)` 读取 best_move、`advanced(by: 24)` 读取 pv）搬到 EmbeddedPikafishEngine 后，改为**结构体字段访问**（`result.pointee.best_move` 等），消除所有硬编码偏移量。

**具体改动清单：**

1. **EmbeddedPikafishEngine：**
   - 新增 `private let cApiQueue = DispatchQueue(label: "com.chinesechess.pikafish.capi")`
   - bestMove 的 `DispatchQueue.global()` → `cApiQueue`
   - 新增 `evaluate()` 和 `multiPV()` 方法，用 `cApiQueue` + 结构体字段访问
2. **PositionAnalyzer：**
   - 删除所有直接 C API 调用（`pikafish_eval`、`pikafish_multi_pv`、`UnsafeMutablePointer` 操作、`ensureEngineReady()`）
   - 通过 EngineRouter.shared 获取共享 EmbeddedPikafishEngine 实例

```swift
actor PositionAnalyzer {
    static let shared = PositionAnalyzer()

    private func getEngine() async -> EmbeddedPikafishEngine {
        let engine = await EngineRouter.shared.switchEngineIfNeeded()
        guard let emb = engine as? EmbeddedPikafishEngine else {
    // P2-6: 不用 fatalError，返回 nil + 日志，分析中断优于崩溃
    private func getEngine() async -> EmbeddedPikafishEngine? {
        let engine = await EngineRouter.shared.switchEngineIfNeeded()
        guard let emb = engine as? EmbeddedPikafishEngine else {
            NSLog("[PositionAnalyzer] Engine is not EmbeddedPikafishEngine, analysis disabled")
            return nil
        }
        return emb
    }

    func evaluate(fen: String, moveHistory: [String]) async -> AnalysisLine? {
        guard let engine = await getEngine() else { return nil }
        return await engine.evaluate(fen: fen, moveHistory: moveHistory,
                                      depth: analysisDepth, timeMs: analysisTimeMs)
    }
}
```

**串行队列的副作用：** 长时间分析（evaluate depth=18, time=2000ms）会阻塞 bestMove 排队。

**P1-7 回应：pikafish_stop() 线程安全**

`pikafish_api.h` 明确声明：`pikafish_stop()` 是 “thread-safe, non-blocking, can be called from any thread at any time”。它设置 volatile flag，不走 cApiQueue。

当前 `EmbeddedPikafishEngine.stopSearch()` 已声明为 `nonisolated`，可以从任意线程调用。中断流程：
```
对弈请求 bestMove → actor 锁获取 → 调 stopSearch()（nonisolated，不排队）
→ pikafish_stop() 设置 volatile flag → cApiQueue 中正在执行的分析搜索检测到 flag 并返回
→ bestMove 获取 cApiQueue 执行权
```

无需额外机制，现有 `pikafish_stop()` + volatile flag 已满足需求。

**回归风险：** 中。搜索逻辑不变，但串行队列改变了 C 调用时序——需验证分析不会导致对弈走子卡顿。

#### #2 Models 解除对 Services 的反向依赖（P0, D1）

**现状分析：**

8 个 Model 文件直接引用 Services 层：
- `Board.swift` → `FENParser.parse(fen:)`（Services 层）
- `UnlockedFeature.swift` → `L10n.shared.t()`（Services 层，10 处）
- `PlayerProfile.swift` → `L10n.shared.t()`（Services 层，7 处）
- `Puzzle.swift` → `L10n.shared.t()`（Services 层，3 处）
- `PuzzleChapter.swift` → `L10n.shared.t()`（Services 层，2 处）
- `Achievement.swift` → `L10n.shared.t()`（Services 层，4 处）
- `DailyChallenge.swift` → `PuzzleStore.shared`（Services 层，2 处）
- `MoveQuality`（在 PositionAnalyzer.swift 中） → `L10n.shared.t()`（Services 层）

**修复方案：**

按违反类型分三种处理：

**类型 A：Board → FENParser（逻辑依赖）**

Board 的 `init(fen:)` 调用 `FENParser.parse()`。

方案：提取到 `Models/FENDecoder.swift`（纯解析，无 Service 依赖），Board 和 FENParser 都调用它。FENParser（Services 层）变为薄封装。

**类型 B：Model → L10n（显示依赖，6 个文件）**

Model 层不应直接做 i18n。L10n 调用应上推到 View/ViewModel 层。

方案：
- `UnlockedFeature` / `PlayerProfile` / `Puzzle` / `PuzzleChapter` / `Achievement` 的 `localizedLabel()` / `title` / `subtitle` 等方法返回 **L10n key（String）** 而非翻译后的文本
- View/ViewModel 调用 `L10n.shared.t(model.displayKey)` 做翻译

示例：
```swift
// 改动前（Model 层）
var rankLabel: String { L10n.shared.t("rank.\(rawValue)") }

// 改动后（Model 层）
var rankL10nKey: String { "rank.\(rawValue)" }
// ViewModel/View 层调用：L10n.shared.t(profile.rankL10nKey)
```

**P1-4 补充：L10n 结果持久化验证**

已 grep 确认：6 个 Model 中 `L10n.shared.t()` 的返回值**没有被持久化**：
- `UnlockedFeature` / `PlayerProfile` / `Achievement`：L10n 返回值仅用于 computed property（`localizedLabel` / `displayName`），不参与 Codable 编码
- `DailyChallengeMode` / `DailyStreakReward`：`localizedTitle` / `localizedDesc` 是 computed property，`DailyChallenge` 的 Codable 字段（date / mode / puzzleId / completed / score）不含 L10n 输出
- `Puzzle`：`typeName` 是 computed property，Codable 编码的是 rawValue

结论：L10n key 上推安全，不会影响持久化数据。

**类型 C：DailyChallenge → PuzzleStore（数据依赖）**

DailyChallengeManager 通过 `PuzzleStore.shared.puzzles` 获取数据（DailyChallenge.swift:152, 161）。

方案：方法接受 puzzles 数组作为参数，调用方负责传入。

**P1-3 补充：调用方枚举**

| 调用方 | 位置 | 传入方式 |
|--------|------|----------|
| `DailyChallengeView` | `Views/DailyChallengeView.swift:6` | `DailyChallengeManager.shared`，可改为 init 时注入 puzzles 或方法参数 |
| `ChineseChessApp`（macOS）| `App/ChineseChessApp.swift:406` | 通过 DailyChallengeView 间接调用 |
| `ChineseChessiOSApp` | `App/ChineseChessiOSApp.swift:257` | 同上 |

所有调用方都在 View 层，能自然获取 `PuzzleStore.shared.puzzles` 并注入。

**回归风险：** 中。涉及 8 个文件，但改动模式统一（接口签名变化）。需要同步修改所有调用方。

#### #3 GameViewModel 补 halfmoveClock（P0, D1）

**现状分析：**

PuzzleViewModel 已实现 halfmoveClock（50 回合规则），GameViewModel 缺失。当前 GameViewModel 的和棋检测只有三次重复和困毙/长将。

**修复方案：**

参照 PuzzleViewModel 的实现，在 GameViewModel 中添加：

1. 新增 `private var halfmoveClock: Int = 0`
2. 在 `movePiece()` 中：
   - 吃子 → `halfmoveClock = 0`
   - 非吃子 → `halfmoveClock += 1`
3. 在和棋检测中新增：`if halfmoveClock >= 100 { return true }`（100 半回合 = 50 完整回合）
4. 在 `newGame()` 中重置：`halfmoveClock = 0`

**注意事项：**
- halfmoveClock 的计数时机必须和 PuzzleViewModel 一致（在走法执行后、状态检查前）
- **P2-1 采纳：** 悔棋时 halfmoveClock 用 `MoveRecord` 存快照值（`moveHistory` 中每步记录当时的 halfmoveClock），undo 时恢复快照，不做减计

**回归风险：** 低。新增逻辑不影响现有走法流程，只在和棋判定时多一个条件。

#### #7 ZobristHash 启用增量更新（P1, D6）

**现状分析：**

`ZobristHash.update(hash:piece:from:to:captured:)` 已完整实现，但 AIEngine 的 negamax 和 rootSearch 中每个节点都调 `ZobristHash.hash(board:)` 全量重算。negamax 递归树展开后节点数可达数十万，每次全量遍历 32 格棋盘浪费严重。

**修复方案：**

1. **AIEngine.bestMove / rootSearch 入口处计算初始 hash（全量）**
2. **board.execute(move) 时增量更新 hash**
3. **board.undoLastMove() 时回退 hash**

具体实现路径：

```swift
// rootSearch 内：
var currentHash = ZobristHash.hash(board: board)
for move in orderedMoves {
    let childHash = ZobristHash.update(hash: currentHash, piece: move.piece,
                                        from: move.from, to: move.to, captured: move.captured)
    board.execute(move)
    // 将 childHash 传入 negamax 作为参数
    let score = -negamax(board: board, hash: childHash, depth: ...)
    board.undoLastMove()
}
```

**P1-2 补充：增量验证策略**

1. **Spike 验收标准：** ≥20 个已知局面（含吃子、将军、非吃子、将帅对面等），每个局面验证 `ZobristHash.update(...)` 增量结果 == `ZobristHash.hash(board:)` 全量结果
2. **Board 是 class（`@Observable class Board`）**，非 struct。execute/undoLastMove 是原地修改，hash 传递方式为：execute 前算 childHash，传入子搜索，undo 后恢复 parentHash（不需要从 board 重算）
3. **子搜索路径的 hash 传递：**
   - **quiescence search：** 同 negamax，execute 前增量算 hash，传入递归调用
   - **null-move pruning：** `board.toggleTurn()` 只翻转行棋方，hash 变化为 `currentHash ^ ZobristHash.sideHash`（两次 toggle 恢复原 hash）
   - **null-move 内的 negamax 递归：** 传入翻转后的 hash

**性能预期：** 搜索阶段减少 15-25% 的哈希计算开销（审计报告估算）。

**回归风险：** 中。增量更新正确性必须严格验证——一个 bit 的错误会导致 TT 命中率暴跌甚至搜索结果错误。需对比改动前后同一局面的搜索结果。

### Phase 2B：TT 内存 + AIEngine 实例复用

**目标：** 消除多 AIEngine 实例的 TT 内存浪费，统一实例管理。

#### #8 TT 内存优化 + AIEngine 实例复用（P1, D6）

**现状分析：**

两个问题叠加：

1. **TranspositionTable 实例级：** 每个 AIEngine 实例创建独立的 TranspositionTable。macOS 默认 1<<20 = 1,048,576 条目 × 2 桶 × ~56 字节/条 ≈ 112MB。PuzzleViewModel 直接创建 AIEngine（`private let aiEngine = AIEngine()`），GameViewModel 通过 EngineRouter 也可能持有 AIEngine，两个实例合计 ~224MB。

2. **EmbeddedPikafishEngine TT 配置：** `configureTTSize()` 在 start() 中调用，但 PositionAnalyzer 绕过 start() 直接调 C API。统一入口后（#1 完成），TT 配置可被正确管理。

**修复方案：**

**方案 A：AIEngine 实例复用（消除多实例 TT）**

PuzzleViewModel 不再直接 `AIEngine()`，改为通过 `EngineRouter.shared.getNativeEngine()` 复用单例。

```swift
// 改动前（PuzzleViewModel）
private let aiEngine = AIEngine()  // ← 新建实例，独立 TT

// 改动后
private var aiEngine: AIEngine { EngineRouter.shared.getNativeEngine() }
```

这样全 App 只有一个 AIEngine 实例，一个 TranspositionTable。

**P0-3 修正：共享 AIEngine 的并发安全**

AIEngine 声明为 `actor AIEngine: AIEngineProtocol`。actor 隔离保证：
- 两个 ViewModel 同时调用 `bestMove()` → actor 串行执行，无 data race
- `clearHistory()` 与 `bestMove()` → actor 串行执行，不会在搜索中途清空

**但有一个语义问题：** PuzzleViewModel 新开局时调 `clearHistory()`，如果 GameViewModel 的搜索正在排队等待 actor 锁，搜索会在 clearHistory 之后执行——moveOrderer 已清空，搜索质量下降（但不会崩溃，TT 用 hash 校验）。

**缓解措施：** `clearHistory()` 只清 moveOrderer（历史启发表），不清 TT（置换表跨对局复用是正常的）。当前实现已如此（`clearHistory()` 只调 `moveOrderer.clearHistory()`，TT 不 clear），**无需额外改动**。

**方案 B：TranspositionTable 内存优化（可选增强）**

- **P2-5 采纳：** 触发条件为单实例 TT > 150MB
- 紧凑布局：ContiguousArray 或 UnsafeMutablePointer 池化
- 当前每条 TTEntry ≈ 18 字节裸数据 + Swift struct 对齐开销

推荐：先做方案 A（消除多实例），观察内存。如果单实例 TT > 150MB，再做方案 B。

**前置条件：** #1（PositionAnalyzer 统一入口）必须完成。

### Phase 4：iOS Sheet 统一管理

**目标：** 将 iOS 端 14 个独立 `.sheet()` / `.fullScreenCover()` 统一为单一入口。

#### #4 iOS Sheet 统一管理（P0, D1）

**现状分析：**

macOS 端在 v3.7.1 已完成统一 sheet 管理（`SheetDestination` 枚举 + `activeSheet` 状态）。iOS 端 `ChineseChessiOSApp.swift` 仍有 14 个独立的 `.sheet(isPresented:)` / `.fullScreenCover(item:)` 调用。

已知问题：macOS 曾因多 `.sheet` 串联导致卡死（v3.7.1 P0 bug），iOS 存在同样风险。

**当前 iOS sheet 清单（14 个）：**

| # | 类型 | 触发状态 |
|---|------|----------|
| 1 | `.sheet` | `showImportFailAlert`（alert 伪装成 sheet）|
| 2 | `.sheet` | `showPuzzles` |
| 3 | `.fullScreenCover` | `toolbarReplayRecord` |
| 4 | `.sheet` | `showHistory` |
| 5 | `.fullScreenCover` | `historyReplayRecord` |
| 6 | `.sheet` | `showImportFailAlert`（重复）|
| 7 | `.sheet` | `showThemePicker` |
| 8 | `.sheet` | `showSettings` |
| 9 | `.sheet` | `showDailyChallenge` |
| 10 | `.sheet` | `showAchievements` |
| 11 | `.sheet` | `showRankPrivilege` |
| 12 | `.sheet` | `showAnalysis` |
| 13 | `.sheet` | `showCoach` |
| 14 | `.sheet` | `showOpeningExplorer` |

**修复方案：**

参照 macOS 的 `SheetDestination` 枚举，为 iOS 创建统一的 sheet/cover 管理器。

1. **定义 iOS 专用枚举（复用 macOS 模式）：**

**P1-1 修正：保留 sheet 和 fullScreenCover 两个入口**

sheet 允许下滑 dismiss，fullScreenCover 不允许。回放界面误触下滑会丢失进度。枚举增加 `isFullScreen` 属性区分：

```swift
enum iOSSheetDestination: Identifiable {
    case puzzles
    case history
    case themePicker
    case settings
    case dailyChallenge
    case achievements
    case rankPrivilege
    case toolbarReplay(GameRecord)   // fullScreenCover
    case historyReplay(GameRecord)   // fullScreenCover
    case analysis(GameRecord)
    case coach(GameRecord)
    case openingExplorer

    var isFullScreen: Bool {
        switch self {
        case .toolbarReplay, .historyReplay: return true
        default: return false
        }
    }

    var id: String { ... }
}
```

2. **两个呈现入口：**

```swift
@State private var activeSheet: iOSSheetDestination?

// sheet 入口（非全屏）
.sheet(item: Binding<iOSSheetDestination?>(
    get: { activeSheet?.isFullScreen == false ? activeSheet : nil },
    set: { if $0 == nil { activeSheet = nil } }
)) { destination in
    switch destination { ... }
}

// fullScreenCover 入口（全屏）
.fullScreenCover(item: Binding<iOSSheetDestination?>(
    get: { activeSheet?.isFullScreen == true ? activeSheet : nil },
    set: { if $0 == nil { activeSheet = nil } }
)) { destination in
    switch destination { ... }
}
```

3. **所有触发点改为设置 `activeSheet`：**

```swift
// 改动前
Button(...) { showSettings = true }
.sheet(isPresented: $showSettings) { SettingsView() }

// 改动后
Button(...) { activeSheet = .settings }
```

4. **P2-2 采纳：** 清理 `showImportFailAlert` 重复声明（#1 和 #6 两个 sheet 指向同一 alert），保留一个 `.alert()` 入口

**注意事项：**
- alert（showImportFailAlert）不应纳入 sheet 统一管理，保持独立的 `.alert()`
- 需测试每个 sheet 的 dismiss 逻辑是否正常（dismiss 后 activeSheet 应自动置 nil）
- **P2-7：** 当切换目标跨 isFullScreen 类型时（如从 fullScreen replay 切到 sheet settings），先置 `activeSheet = nil`，下一 runloop 再赋新值，避免 SwiftUI 过渡状态异常

**回归风险：** 中。涉及所有 iOS 弹出视图的呈现逻辑。每个 sheet 的生命周期（数据传递、dismiss 回调）都需要逐一验证。建议改动后逐个 sheet 手动测试。
