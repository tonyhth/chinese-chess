# v3.4.0 macOS 静态库嵌入 — 通用设计

> iOS 引擎集成完成后，macOS 同步改为静态库嵌入，与 iOS 共用同一套引擎集成层。
>
> **前置条件**：iOS 引擎集成（Phase 1-6）已完成。
>
> **版本号**：macOS 嵌入 + iOS 嵌入统一在 v3.4.0 完成。

---

## 背景

### 当前状态

| 平台 | 当前方案 | 问题 |
|------|----------|------|
| macOS | 外部进程 + stdin/stdout 管道 | 用户需单独下载配置 pikafish，体验差 |
| iOS | 静态库嵌入（Phase 1-6 已完成） | 无 |

### 目标

macOS 改为预编译静态库嵌入，**iOS/macOS 统一迁移到 modulemap 方案**，删除 ObjC 中间层，Swift 直接调用 C API。

| 平台 | 编译架构 | NNUE |
|------|----------|------|
| iOS device | arm64 | 嵌入（70MB 大网络） |
| iOS simulator | arm64 / x86_64 | 嵌入 |
| macOS | x86_64 / arm64 | 嵌入（70MB 大网络） |

### 收益

1. **用户体验**：macOS 用户开箱即用，无需下载配置 pikafish
2. **架构统一**：iOS/macOS 共用 C API + Swift Actor，无 ObjC 中间层
3. **性能**：进程内调用比管道通信更快（无序列化/反序列化开销）
4. **稳定性**：无进程管理问题（启动失败、僵尸进程、管道断裂等）
5. **代码精简**：删除 ObjC Wrapper（PikafishEngine.h/m），Swift 直接调用 C API
6. **单文件实现**：iOS/macOS 共用一个 `EmbeddedPikafishEngine.swift`，无 `#if os()` 分支

## 核心架构变更（vs 原 iOS 方案）

原 iOS 方案为 `C API → ObjC Wrapper → Swift Actor` 三层。本次方案 **iOS/macOS 统一简化为 `C API → Swift Actor` 两层**：

```
原 iOS 架构（已实施）：
  EmbeddedPikafishEngine → PikafishEngine (ObjC) → pikafish_api (C)

新统一架构（iOS + macOS）：
  EmbeddedPikafishEngine → pikafish_api (C)  ← 通过 modulemap 直接桥接
```

### 为什么去掉 ObjC 中间层

1. **Swift C 互操作成熟**：Swift 可以直接通过 modulemap 导入 C 头文件，无需 ObjC 桥接
2. **减少代码层级**：删除 PikafishEngine.h/m（ObjC Wrapper），少一层间接调用
3. **维护成本降低**：不需要维护 ObjC Wrapper 的内存管理、线程转换
4. **编译简化**：不需要 ObjC 编译目标，纯 Swift + 预编译静态库
5. **iOS/macOS 完全统一**：一个 `EmbeddedPikafishEngine.swift`，无 `#if os()` 条件 import

### iOS 侧迁移

原 iOS 方案已实施 ObjC Wrapper。本次 macOS 方案同时将 iOS 侧也迁移到 modulemap：
- 删除 `PikafishEngine.h` / `PikafishEngine.m` / bridging header 相关引用
- iOS 同样使用预编译 `libpikafish.a` + modulemap
- **收益**：消除了"iOS 用 ObjC、macOS 用 modulemap"的双轨维护

## C API 线程安全模型

> **P0-1 修复**：明确 C API 线程模型，确保 actor 不会阻塞 UI。

### 线程模型定义

| 函数 | 行为 | 线程安全 |
|------|------|----------|
| `pikafish_init()` | 同步，加载 NNUE + 初始化全局状态 | ❌ 非线程安全，仅在 `start()` 中调用 |
| `pikafish_best_move()` | **同步阻塞**：阻塞调用线程直到搜索完成或 `stop` 被调用 | ❌ 非线程安全，同一时刻仅允许一个调用 |
| `pikafish_stop()` | 设置 `volatile std::atomic<bool>` 停止标志 | ✅ 线程安全，可从任意线程调用 |
| `pikafish_new_game()` | 同步，重置搜索表 | ❌ 非线程安全，需在非搜索期间调用 |
| `pikafish_set_option()` | 同步，设置 UCI 选项 | ❌ 非线程安全，需在非搜索期间调用 |
| `pikafish_quit()` | 同步，释放全局资源 | ❌ 非线程安全，需在非搜索期间调用 |
| `pikafish_get_version()` | 同步，返回静态字符串指针 | ✅ 线程安全（返回编译时常量） |

### Actor 如何保证安全

`EmbeddedPikafishEngine` 是 Swift actor，**串行执行所有方法**，天然保证：
- `pikafish_best_move()` 不会被并发调用
- `pikafish_stop()` 可以从 actor 外部调用（只设置原子标志，不违反串行约束）
- `pikafish_quit()` 只在 `shutdown()` 中调用，不会与 `best_move` 并发

### 阻塞问题的应对

`pikafish_best_move()` 是同步阻塞调用（搜索可能持续数秒到数十秒）。Swift actor 默认在 cooperative thread pool 执行，C 函数阻塞会占据一个 cooperative 线程。

**解决方案**：在 actor 内部通过 `withCheckedThrowingContinuation` + 后台线程执行阻塞调用：

```swift
func bestMove(fen: String, moves: [String], difficulty: AIDifficulty) async -> String {
    guard isReady else { return "0000" }
    let depth = mapDifficultyToDepth(difficulty)

    return await withCheckedThrowingContinuation { continuation in
        DispatchQueue.global(qos: .userInitiated).async {
            var buffer = [CChar](repeating: 0, count: 32)
            let movesStr = moves.joined(separator: " ")
            let result = fen.withCString { fenCStr in
                movesStr.withCString { movesCStr in
                    pikafish_best_move(fenCStr, movesCStr, Int32(depth), 0, &buffer, Int32(buffer.count))
                }
            }
            if result == 0 {
                let move = String(cString: buffer)
                continuation.resume(returning: move)
            } else {
                // 搜索被中断或失败，返回当前 buffer 中的部分结果
                let move = String(cString: buffer)
                continuation.resume(returning: move.isEmpty ? "0000" : move)
            }
        }
    }
}
```

**关键点**：
- 阻塞的 `pikafish_best_move()` 在 `DispatchQueue.global()` 执行，**不占用 cooperative pool**
- `withCheckedThrowingContinuation` 让 actor 方法可以 `await` 等待，但不阻塞 actor executor
- UI 线程（MainActor）不受影响

### stopSearch 跨 actor 调用

`pikafish_stop()` 只设置原子标志，不违反 actor 隔离。但 Swift actor 隔离规则不允许从外部直接调用 actor 内部方法。

**实现**：`stopSearch()` 是 actor 方法，内部调用 `pikafish_stop()`。调用方需 `await engine.stopSearch()`。如果需要同步中断（不等待 actor 调度），可暴露一个 `nonisolated` 方法直接调用 C API：

```swift
nonisolated func stopSearchImmediate() {
    pikafish_stop()  // 原子操作，线程安全，无需 actor 隔离
}
```

## pikafish_stop() 中断行为定义

> **P0-2 修复**：明确定义 stop 中断后的返回值和 buffer 状态。

### 行为定义

| 场景 | `pikafish_best_move()` 返回值 | buffer 内容 | 调用方处理 |
|------|------------------------------|-------------|-----------|
| 正常完成 | `0`（成功） | 最佳走法 UCI 字符串（如 `"e2e4"`） | 直接使用 |
| 被 `pikafish_stop()` 中断 | `-1`（搜索中断） | 截至中断时的最佳走法（可能非最优） | 使用 buffer 内容（非空时），否则 fallback |
| 参数错误 | `-2`（无效输入） | 空（全零） | 返回 `"0000"` fallback |

### 中断时序

1. 主线程调用 `bestMove()` → 后台线程开始搜索
2. 用户触发 `stopSearch()` → `pikafish_stop()` 设置原子标志
3. 搜索线程下一次迭代检查到标志 → 立即返回当前最佳走法
4. `pikafish_best_move()` 返回 `-1`，buffer 包含截至中断时的走法

**竞态窗口**：`pikafish_stop()` 在 `pikafish_best_move()` 之前调用 → `pikafish_best_move()` 开始时即检测到停止标志，极短时间后返回 `-1`，buffer 为空。调用方应返回 `"0000"`。

**C API 实现保证**：
- `pikafish_stop()` 使用 `std::atomic<bool>` 标志，无锁，无竞态
- 搜索主循环每次迭代检查停止标志（间隔 < 1ms）
- `pikafish_best_move()` 返回后，buffer 内容是有效的 null-terminated 字符串（即使搜索被中断）

### NNUE 部署（运行时从 Bundle 加载）

> ⚠️ **修正（2026-06-26）**：pikafish 不支持编译时 NNUE 嵌入。`-DNNUE_EMBEDDING_ON` 是无效参数，全源码搜索无匹配。
> 详见 `nnue-embedding-investigation.md`。

NNUE 以 zstd 压缩文件（48MB）打包到 App Bundle Resources 目录，运行时由 `pikafish_api.cpp` 通过
`CFBundleCopyResourcesDirectoryURL` 加载：

1. App 启动 → `pikafish_init()`
2. `CFBundleCopyResourcesDirectoryURL()` 获取 Resources 路径
3. `read_compressed_nnue()` 读取并解压 `pikafish.nnue`
4. `Network::load()` 初始化神经网络
5. 引擎就绪

**为什么不做编译时嵌入**：
- pikafish 源码中没有 NNUE 编译时嵌入机制（无 incbin、无 xxd、无嵌入数据数组）
- `-DNNUE_EMBEDDING_ON` 在代码中无任何引用，是无效参数
- iOS 一直使用运行时加载（project.yml 第 75 行：pikafish.nnue 作为 Copy Bundle Resources）
- 编译时嵌入需修改第三方源码，升级维护成本高
- 最终 App 体积相同（48MB NNUE 数据无论嵌入 .a 还是打包为资源文件都在 App 中）

| 平台 | 当前大小 | 增量 | 新大小 |
|------|----------|------|--------|
| macOS | ~15MB | +48MB（NNUE 资源文件）+ 4MB（引擎代码） | ~67MB |

> macOS App 大小 ~67MB，远低于原方案错误预估的 85MB。

## 平台差异处理

### 内存控制

> **P1-4 修复**：基于物理内存动态设置，不再硬编码。

iOS 和 macOS 均基于物理内存动态设置 TT size：

```swift
private func configureTTSize() {
    let physicalMemory = ProcessInfo.processInfo.physicalMemory
    let ttSizeMB: Int

    #if os(iOS)
    // iOS：保守策略（后台内存压力更大）
    if physicalMemory < 2_000_000_000 {
        ttSizeMB = 16
    } else if physicalMemory >= 4_000_000_000 {
        ttSizeMB = 64
    } else {
        ttSizeMB = 32
    }
    #else
    // macOS：基于物理内存的 10%，上限 256MB，下限 64MB
    // 8GB RAM → 819MB * 10% ≈ 82MB → 82MB
    // 16GB RAM → 1638MB * 10% ≈ 164MB → 164MB
    // 32GB RAM → 3277MB * 10% ≈ 328MB → 256MB (上限)
    // 4GB RAM (虚拟机) → 410MB * 10% ≈ 41MB → 64MB (下限)
    let dynamicMB = Int(physicalMemory / 10 / 1_000_000)
    ttSizeMB = max(64, min(dynamicMB, 256))
    #endif

    pikafish_set_option("Hash", String(ttSizeMB))
}
```

**依据**：
- pikafish 基础内存占用（NNUE 解压后约 200MB 在内存中 + 搜索栈 + 评估缓冲）约 250-300MB
- TT size 占物理内存 10% 是 ChessBase/Stockfish 社区经验值
- 上限 256MB：避免极端配置下内存浪费
- 下限 64MB：保证搜索质量
- macOS App 总内存 ≈ 300MB(基础) + TT size，8GB Mac 上约 382MB

### 难度映射（共用）

macOS 和 iOS 共用难度映射，避免平台差异导致走棋风格不同：

```swift
private func mapDifficultyToDepth(_ difficulty: AIDifficulty) -> Int {
    switch difficulty {
    case .beginner: return 2
    case .easy: return 5
    case .medium: return 10
    case .hard: return 18
    case .master: return 24
    }
}
```

## info 回调处理

**v3.4.0**：不实现 info 回调

- 嵌入引擎不提供实时搜索信息
- UI 只显示"思考中..."状态
- 走棋完成后直接显示结果

**后续版本**：增加 info callback

- C API 增加回调注册函数：`pikafish_set_info_callback(void (*callback)(const char* info_line))`
- Swift Actor 直接接收回调，转发给 UI

**承诺**：v3.4.0 发布后立即规划 info callback 实现（目标 v3.4.1 或 v3.5.0）。

**已知功能退化**（v3.4.0 相比外部进程方案）：
- ❌ 实时搜索信息（depth/score/nps/pv）不可用
- ❌ UCI 调试输出不可用（高级用户排查问题用）
- ✅ 走棋结果正确性不受影响
- ✅ 引擎启动/停止/切换不受影响

> **发布决策**：功能退化可接受。info 回调承诺 v3.4.1/v3.5.0 补上，间隔可控。UCI 调试能力仅影响极少数高级用户，可通过日志文件（pikafish 输出到 stderr）间接获取。

## C API 返回格式定义

> **P1-6 修复**：明确 `pikafish_best_move()` 返回格式。

`pikafish_best_move()` 向 buffer 写入的内容：

- **格式**：纯 UCI 走法字符串，null-terminated（如 `"e2e4"`、`"h2e2"`）
- **不含**：`"bestmove"` 前缀、`"ponder"` 后缀
- **长度**：4-5 字符（中国象棋 UCI 走法格式：起点+终点，如 `h2e2`；含升变时 5 字符如 `a0a1q`）
- **buffer 建议大小**：32 字节（远超实际需要，留足余量）

```swift
var buffer = [CChar](repeating: 0, count: 32)  // 32 bytes，足够容纳任何 UCI 走法
```

## 现有外部进程方案的迁移策略

### 完全替换 + 紧急回退开关

**替换理由**：
1. 嵌入方案开箱即用，外部进程方案需要用户下载配置
2. 保留两套方案意味着维护 ExternalEngineManager + UCITransceiver + Pipe + Process 全部代码
3. 进程管理问题（启动失败、僵尸进程、管道断裂）消失
4. 架构简化：删除大量旧代码

**紧急回退**（P2-12）：

保留编译期 feature flag，可紧急切回外部进程方案：

```swift
// 编译期开关（默认 false，紧急时设为 true 重新编译发布）
#if DEBUG_ENABLE_EXTERNAL_ENGINE_FALLBACK
// 保留 ExternalEngineManager 代码路径（仅 debug / 紧急发布用）
#endif
```

- 正式发布：`DEBUG_ENABLE_EXTERNAL_ENGINE_FALLBACK = false`，外部进程代码不编译
- 紧急回退：设为 `true`，重新编译发布，外部进程代码恢复可用
- 不增加正式版的维护成本（feature flag 控制代码是否参与编译）

> **决策**：v3.4.0 正式版不保留外部进程运行时开关。紧急回退通过编译开关实现，不需要运行时双轨。

## 风险点

| 风险 | 影响 | 回退方案 |
|------|------|----------|
| modulemap 配置问题导致 Swift import 失败 | 阻塞 | Xcode modulemap 调试，必要时用 bridging header 过渡 |
| 预编译静态库架构不匹配 | 链接失败 | 确保 universal binary，`lipo -info` 验证 |
| 旧外部引擎配置升级冲突 | 配置残留 | EngineConfigStore 迁移：旧配置静默忽略 |
| info 回调缺失 | UI 无搜索信息 | v3.4.0 先不实现，后续增加 |
| macOS App 大小 | ~67MB | 可接受 |
| pikafish 特定 macOS 版本崩溃 | 运行时崩溃 | 编译期 feature flag 切回外部进程方案 |
| C 函数阻塞 cooperative pool | UI 卡顿 | bestMove 在 DispatchQueue.global() 执行（见线程模型章节） |
| NNUE 文件未打包到 Bundle Resources | 引擎初始化失败 | 确认 Copy Bundle Resources 包含 pikafish.nnue |
| MACOSX_DEPLOYMENT_TARGET 不一致 | 运行时崩溃 | 构建脚本锁定为 13.0，与 App 一致 |
