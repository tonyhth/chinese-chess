## 1. 数据模型：变招随 envelope 落盘

**现状痛点**：multiPV 分析时 topN 着法只用于质量定级后被丢弃——回看无据。

**设计**：`MoveAnalysis` 增可选字段 `variations: [Variation]?`（Codable 可选，老档 nil 自动兼容，同 isQuickResult 先例）：

```
Variation { let uci: String; let sanZh: String   // 如 "马8进7"
            let cpAfter: Int                       // 该变招后引擎评估（红方视角）
            let rank: Int }                        // 1...3
```

- **只存 top3**（P95 曲线点选需求即 3 条，存储增量 ≤ ~120B/着，25-70KB/局估算不变档）；
- **深度档绑定**：variations 随 envelope 的 engineVersion/depthSetting 过期机制整体失效重算（decision v1.1 既有链，不另造第二套过期）；
- **写入时机**：与 evalSequence 同批次——定级计算本就得 multiPV，顺手截 top3 入 MoveAnalysis，零额外引擎调用。

## 2. 变招 API 草案（C4 消费接口，P9 芯层）

```swift
/// 评估域对展示层的唯一供给口（P9 芯 / P1 速览 / CoachExplainer 共用）
protocol AnalysisPresentationProvider {
  /// 局面 k 的 top3 变招（k = 第 k 着后的局面；与持久化 analyzedMoveCount 前缀、
  /// 原型曲线点击"局面口径"三方同构——off-by-one 只允许定义一次）
  func variations(atPosition k: Int) -> [Variation]
  /// 三要素：实际着法 / 引擎推荐 / 亏损 cp（第 i 着，i=k-1）
  func moveReview(atMove i: Int) -> MoveReview      // { played, recommended, lossCp }
  /// 供 CoachExplainer：局面+变招打包（数据供给，不改其场景逻辑）
  func coachingPayload(atPosition k: Int) -> CoachingPayload
}
```

- 实现挂 `AnalysisEnvelopeStore`（A2 产物）之后，读 sidecar 即得，**回看零引擎调用**（吃①红利）；
- **lossCp 口径**：引用质量定级阈值常量同源（不双轨，plan §0.5 B 组约束延续）——A1 常量上提后从共享 Model 层引；
- 消费方时序：P1 速览可先用 moveReview 三要素；P9 芯（C4）用全量；CoachExplainer 打通评审时定是否新增"变招讲解"场景（26 场景池）。

## 5. 验收锚

1. 点开任一标注三要素齐全且 lossCp 与该步定级同源（阈值常量引用，无硬编码）；
2. 曲线任一点 top3 可见；断网/引擎不可用回看仍可用（sidecar 数据）；

4. 深度档切换 → variations 随 envelope 过期重算（不出现新旧混排）；
5. 引擎面零回归：multiPV 消费层改动后 baseline 六断言复测全绿。
