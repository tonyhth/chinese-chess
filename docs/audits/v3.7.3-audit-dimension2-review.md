## 发现 1：PositionAnalyzer 与 EmbeddedPikafishEngine C 层并发竞争

### 复核结论：P0 ✅ 确认，补充了验证细节和两个新路径（UAF 精确路径 + actor 注释误导性）

Ruby 的分析链条完整准确。我逐条验证了 C 层源码，补充以下确认：

**1. `pikafish_eval` / `pikafish_multi_pv` 确实直接调用 `pikafish_best_move`**

```cpp
// pikafish_api.cpp:455
int ret = pikafish_best_move(fen, moves, depth, time_ms, move_buf, sizeof(move_buf));
```

这意味着所有三条 C API 入口（`pikafish_best_move`、`pikafish_eval`、`pikafish_multi_pv`）共享同一套两阶段锁模型和全局状态。

**2. 两阶段锁模型的并发窗口确认**

Phase 2 CV wait 期间 mutex 释放（C++ `g_search_cv.wait(lock, ...)` 释放 mutex），此时另一个调用者可以进入 Phase 1，执行 `g_engine->set_position()` 和 `g_engine->go()`。这会：

- 修改引擎内部 Position 对象，而搜索线程可能正在读取
- 启动新搜索，引擎内部会 `stop()` 旧搜索线程（Pikafish Engine::go() 内部调 `main_thread->wait_for_search_finished()` 再启动新搜索），旧搜索的 callback 被触发

**3. `g_bestmove_result` 交叉读取确认**

Call B 的搜索完成后 callback 写入 `g_bestmove_result`，此时 Call A 的 Phase 2 从 CV 醒来读取——拿到的是 Call B 的结果。对弈方拿到分析方的走法。

**4. Use-After-Free 确认**

`EmbeddedPikafishEngine.shutdown()` 的 `activeSearchCount` 仅追踪通过 `bestMove()` 发起的搜索。PositionAnalyzer 绕过此计数器直接调 C API。当 shutdown() 检测到 activeSearchCount=0 并执行 `pikafish_quit()` → `delete g_engine` 时，PositionAnalyzer 的搜索可能仍在 C 层运行。这是**真实的 UAF 路径**。

**5. 触发路径现实性**

我验证了 `ChineseChessApp.generateReviewCard()` 确实创建了独立的 `AnalysisViewModel()` 实例并调用 `analyzeAll()`，而用户随时可以点"新局"触发 `GameViewModel.triggerAIMove()`。两条路径同时活跃是完全可能的。

**6. PositionAnalyzer 自身的注释具有误导性**

```swift
/// 局面分析器（actor，线程安全）
/// 分析请求通过 actor 串行化，避免与对弈的 bestMove 并发冲突。
```

这个注释暗示 actor 隔离足以避免冲突，但实际上两个不同 actor（PositionAnalyzer 和 EmbeddedPikafishEngine）无法通过 actor 隔离互斥——它们各自在不同的 executor 上串行执行，但可以同时进行。actor 隔离只保证同一 actor 内的方法串行，不保证跨 actor 互斥。

### 修复方案评估

| 方案 | 安全性 | UX 影响 | 实现复杂度 | 推荐度 |
|------|--------|---------|-----------|--------|
| **A: PositionAnalyzer 通过 EmbeddedPikafishEngine 调用** | ✅ 安全 | ⚠️ 分析阻塞对弈 | 低 | 🟢 短期首选 |
| **B: C 层加全局搜索锁** | ✅ 安全 | ⚠️ 阻塞 actor 线程 | 中 | 🟡 不推荐 |
| **C: 独立引擎实例** | ✅ 最安全 | ✅ 无阻塞 | 高（需改 C API） | 🟢 中期目标 |

**我的建议**：

- **短期（P0 修复）**：方案 A。在 `EmbeddedPikafishEngine` 上新增 `evaluate(fen:moveHistory:depth:timeMs:)` 和 `topMoves(fen:moveHistory:count:depth:timeMs:)` 方法，PositionAnalyzer 改为调用这些方法。actor 隔离天然串行化所有 C 调用。分析会短暂阻塞对弈，但分析请求通常发生在对弈结束或 sheet 中，阻塞窗口极短。

- **shutdown() 修复**：在 `EmbeddedPikafishEngine` 中新增 `private var activeAnalysisCount = 0`，在 evaluate/topMoves 方法中递增递减，shutdown() 等待 `activeSearchCount + activeAnalysisCount == 0`。

- **中期优化**：方案 C。将 C API 改为支持多实例（`pikafish_init()` 返回 handle，所有函数接受 handle 参数），PositionAnalyzer 使用独立引擎实例。这是最干净的解法，但需要重构 C API 层。

## 发现 2：GameRecordStore.findRecordByPuzzleId 在 writeQueue.sync 内做磁盘 I/O

### 复核结论：P1 ⬆️ 升级（原 P2）

这个发现在低频场景下影响不大，但 `writeQueue.sync` 是串行队列，在 sync 内做磁盘 I/O 会阻塞所有写操作。如果 `findRecordByPuzzleId` 在用户交互路径上被调用，50+ 条记录的逐条 JSON 加载会造成可感知的卡顿。

**建议维持 Ruby 的修复方案**：在 `RecordSummary` 中确保 `puzzleId` 字段可用，直接在 summaries 数组上匹配。这是 O(n) 内存操作 vs O(n) 磁盘 I/O 的差别。

## 发现 3：SelfPlayRunner 非 Sendable，可变状态无并发保护

### 复核结论：P2 ✅ 确认

SelfPlayRunner 是 CLI-only 工具，不在用户路径上。当前 `run()` 是串行循环，没有实际并发风险。P2 合理。

**补充建议**：加 `// Not thread-safe. Intended for serial CLI use only.` 注释即可。改为 actor 的成本大于收益。

## 发现 4：SoundEngine.play() 所有播放都 bounce 到主线程

### 复核结论：P2 ✅ 确认

这是性能问题而非安全问题。高速回放场景下主线程压力大，但不会导致崩溃或数据竞争。P2 合理。

**补充**：修复方案简单——创建专用的 `DispatchQueue(label: "audio.playback")` 替代 `DispatchQueue.main`。AVAudioPlayer 的 `play()` 和 `currentTime` setter 都在这个 queue 上执行。

## 发现 5：GameViewModel.fallbackObserver deinit 时序

### 复核结论：P2 ✅ 确认

Swift 运行时对 `NotificationCenter.removeObserver` 在 deinit 中的调用是安全的（它会同步移除注册，之后不会再有回调）。但 Ruby 指出的 "removeObserver 与正在执行的 callback 之间的时序" 是一个理论风险——如果 callback 已经开始执行（在另一个线程上），removeObserver 不会中断它。

当前代码用 `[weak self]` 捕获，即使 callback 在 removeObserver 后短暂执行，self 已释放，callback 内的 `Task { @MainActor in ... }` 不会做任何事。实际风险极低。

P2 合理，改用 Combine subscription 是更 Swift-idiomatic 的写法。

## 遗漏检查

我在复核过程中检查了以下可能被遗漏的并发问题：

1. **EngineRouter 的线程安全性**：`EngineRouter` 是 `@MainActor` 单例，所有方法在主线程执行。`switchEngineIfNeeded()` 在主线程切换引擎，`activeEngine()` 返回当前引擎。如果后台 Task 在切换过程中拿到旧引擎引用并发起搜索，旧引擎的 shutdown 和新搜索可能交叉。但由于 `switchEngineIfNeeded()` 是 await 的，且 Swift 6 的 actor 隔离保证 MainActor 串行，实际风险很低。不升级。

2. **DataMigration.migrateGameHistoryToFiles()** 在 App init 中同步执行，但只做一次且在启动时，不构成并发风险。

3. **PlayerProfileStore** 的 `update` 方法用 `UserDefaults` 做持久化，`UserDefaults` 本身线程安全。无遗漏。
