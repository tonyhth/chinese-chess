## 一、模块间依赖方向

### 发现 1：Models 层反向依赖 Services

- **文件**: Models/Board.swift:120, Models/DailyChallenge.swift:152,161, Models/Achievement.swift:33-37,70,73, Models/PlayerProfile.swift:34-40,271, Models/Puzzle.swift:98-100, Models/PuzzleChapter.swift:104-105, Models/UnlockedFeature.swift:69-78, Models/OpeningTreeNode.swift:113,116
- **级别**: P0
- **问题**: 8 个 Model 文件反向引用 Services 层。具体为：
  - `Board.init(fen:)` 调用 `FENParser.parse()` — 数据模型内部调用解析服务
  - `DailyChallenge` 调用 `PuzzleStore.shared.puzzles` — 数据模型直接访问持久化存储
  - 6 个 Model 调用 `L10n.shared`（Achievement、PlayerProfile、Puzzle、PuzzleChapter、UnlockedFeature、DailyChallenge）— 数据模型包含展示逻辑
  - `OpeningTreeNode` 调用 `ResourceBundle` — 数据模型包含资源定位
  - `PlayerProfile` 调用 `ThemeManager.shared` — 数据模型包含主题管理
  
  注：`GameHistoryStore` 和 `EngineConfigStore` 虽在 Models/ 目录中，但它们本身是 Service（有持久化逻辑和业务方法），属于目录归类错误（见新增发现 19），不作为 Models 反向依赖 Services 计数。
- **建议**: 
  1. `L10n` 移至 Utils/ — 它是纯工具函数，不应留在 Services 导致全层反向依赖
  2. `ResourceBundle` 移至 Utils/ — 资源定位器属于工具
  3. `Board.init(fen:)` 的解析逻辑上移到 FENParser 作为工厂方法
  4. `DailyChallenge` 移除对 `PuzzleStore.shared` 的直接调用，通过依赖注入或上移到 ViewModel

### 发现 2：L10n 目录归类不当

- **文件**: Services/L10n.swift
- **级别**: P1（v2 降级：原 P0）
- **问题**: `L10n` 被所有层引用（Models 8处、AI 2处、ViewModels 7处、Views 27处），但放在 Services 目录。在单 target 项目中，目录分层只是代码组织约定，编译器不做依赖检查——这不会影响运行时行为或功能正确性，但会误导开发者对架构分层的认知。
- **建议**: 将 `L10n` 移至 Utils/ 或新建 Infrastructure/ 目录，改善语义分层。优先级低于功能性 P0。

### 发现 3：多数 View 直接引用 Model 层

- **文件**: Views/ 下 24/29 个文件
- **级别**: P1
- **问题**: View 大量直接使用 `PlayerProfileStore`（12 文件）、`Board`/`Piece`/`Move`（5 文件）、`GameRecord`（5 文件），绕过 ViewModel。
  - **应改**：`PlayerProfileStore.shared` 的直接调用是主要问题——View 既做展示又做数据读取，职责泄漏。
  - **可接受**：棋盘渲染类（Board/Piece/Move）的引用在 MVVM 中有一定合理性——View 是棋盘的渲染器，这些 Model 充当渲染数据。强行套 ViewModel 中间层可能过度设计。
- **建议**: 聚焦修复 `PlayerProfileStore.shared` 的直接调用，在各 ViewModel 中提供只读属性封装。棋盘渲染类的 Model 引用维持现状。

### 发现 4：5 个 View 直接引用 AI 层

- **文件**: Views/AnalysisView.swift, Views/CoachModeOverlay.swift, Views/CoachSessionView.swift, Views/OpeningExplorerView.swift, Views/SettingsView.swift
- **级别**: P1
- **问题**: View 绕过 ViewModel 直接引用 `MoveQuality`、`MoveAnalysis`、`EngineRouter` 等 AI 类型。`SettingsView` 直接调用 `EngineRouter.shared.switchEngineIfNeeded()`。
- **建议**: 
  - `MoveQuality`/`MoveAnalysis` 等展示数据类型应移至 Models/，它们是分析结果的数据模型而非 AI 内部实现
  - `EngineRouter` 的操作应封装到 GameViewModel，View 只触发意图

### 发现 5：ViewModel 之间无循环依赖

- **文件**: N/A
- **级别**: —
- **问题**: 无。`GameViewModel` → `AchievementChecker` 是单向依赖，无循环。
- **建议**: 维持现状。

## 二、AI 模块分析

### 发现 6：AI 模块 5264 行偏大但未失控

- **文件**: AI/ 整个目录
- **级别**: P2
- **问题**: 24 文件平均 219 行/文件，文件粒度合理。但存在 3 个超过 400 行的大文件（AIEngine 660行、CMAESOptimizer 526行、PatternRecognizer 486行），且所有子域平铺在 AI/ 下无子目录区分。
- **建议**: 按功能域重组为 5 个子目录：
  ```
  AI/
  ├── Engine/      (EngineProtocol, EngineRouter, AIEngine, EmbeddedPikafishEngine, UCIMoveConverter)
  ├── Search/      (CheckmateSearch, MoveOrderer, TranspositionTable, TimeManager, ZobristHash, AIConstants)
  ├── Evaluation/  (AIEvaluator, PatternRecognizer, KingSafetyEvaluator, EndgameEvaluator, PositionTables, EvalWeights, EvalConfigManager)
  ├── Opening/     (OpeningBook, OpeningBookExpander)
  └── Tools/       (SelfPlayRunner, CMAESOptimizer, PositionAnalyzer, CoachExplainer)
  ```

### 发现 7：AIEngine.swift 660 行需拆分

- **文件**: AI/AIEngine.swift:1-660
- **级别**: P1
- **问题**: 单文件混合了 Negamax 搜索核心、难度路由、actor 状态管理三大职责。修改搜索算法和调整难度策略需要同时修改同一文件，增加合并冲突风险。
- **建议**: 拆分为 `AIEngine.swift`（actor 状态 + 协议实现，~110行）、`AIEngine+Search.swift`（搜索核心，~350行）、`AIEngine+Difficulty.swift`（难度路由，~200行）

### 发现 8：CMAESOptimizer 跨层耦合

- **文件**: AI/CMAESOptimizer.swift
- **级别**: P2
- **问题**: `EvalWeights` 的反射辅助代码 `setValue` 方法写在了 `CMAESOptimizer.swift` 中，优化器文件包含了权重模型的反射逻辑。另外 `OpeningBook` 和 `OpeningBookExpander` 各自定义了一份 `BookEntry`/`BookFileV2` 结构，存在 DTO 重复。
- **建议**: `EvalWeights` 的反射辅助方法移至 `EvalWeights+Reflection.swift`；`BookEntry`/`BookFileV2` 统一定义在 `OpeningBook.swift` 中，`OpeningBookExpander` 引用同一类型。

### 发现 9：PositionAnalyzer 命名混淆

- **文件**: AI/PositionAnalyzer.swift vs AI/AIEvaluator.swift
- **级别**: P2
- **问题**: `AIEvaluator` 是自研引擎的评估函数，`PositionAnalyzer` 是调用 Pikafish C API 的局面分析器，两者名称容易混淆。
- **建议**: 考虑重命名为 `SearchEvaluator`（原 AIEvaluator）和 `PikafishAnalyzer`（原 PositionAnalyzer），但非紧急——模块内部命名，影响面小。

### 发现 10：AI 对外接口面过大

- **文件**: AI/ 整个目录
- **级别**: P1
- **问题**: AI 模块对外暴露了 11 个符号，包括 `EngineRouter`、`AIDifficulty`、`PositionAnalyzer`、`CoachExplainer`、`MoveQuality`、`MoveAnalysis`、`CoachExplanation`、`GameReviewCard` 等。其中 `AIDifficulty` 被 30+ 处引用，散布在 Models/ViewModels/Views/Services 中；`MoveQuality`/`MoveAnalysis` 是展示层数据模型但留在 AI/ 中。
- **建议**: 
  - `AIDifficulty` 移至 Models/ — 它是游戏设定枚举，非 AI 内部实现
  - `MoveQuality`/`MoveAnalysis`/`CoachExplanation`/`GameReviewCard` 移至 Models/ — 它们是分析结果的数据模型
  - AI 模块只暴露 `EngineRouter`（入口）和 `ChessEngine`（协议），其余通过 Models 间接传递

## 四、新增模块集成质量

### 发现 15：GameViewModel 缺失 halfmoveClock（50 回合规则）

- **文件**: ViewModels/PuzzleViewModel.swift:71,533-551（有 halfmoveClock）；ViewModels/GameViewModel.swift:525-575（缺失）
- **级别**: P0
- **问题**: GameViewModel 已实现三次重复局面判和（`:537`）、困毙判和（`:536`）、长将判负（`:543-575`），但**缺失 halfmoveClock（50 回合无吃子无动兵规则）**。该规则仅在 PuzzleViewModel 的 freePlay 模式中实现。极端场景下（双方反复走子不吃子不进兵），主对弈模式游戏可能无限进行。三次重复局面检测覆盖了大部分实际场景，但 halfmoveClock 是竞赛规则的正式组成部分。
- **建议**: 将 `halfmoveClock` 逻辑提取到共享模块（如 MoveValidator 或新建 DrawDetector），由 GameViewModel 和 PuzzleViewModel 统一调用。

### 发现 16：iOS 端未应用统一 Sheet 管理修复

- **文件**: App/ChineseChessiOSApp.swift:168-315
- **级别**: P0
- **问题**: macOS 端在 v3.7.1 修复了多 `.sheet` 串联导致弹不出的 P0 bug（统一为 `SheetDestination` + 单个 `.sheet(item:)`），但 iOS 端仍使用 14 个独立的 `.sheet`/`.fullScreenCover` 修饰符。iOS 端可能存在相同的 bug 或其变体。同时 iOS 和 macOS 两端 App 文件的 sheet 管理架构完全不同，增加了维护成本和回归风险。
- **建议**: 将 `SheetDestination` 枚举提取为共享类型，iOS 端也迁移到统一的 `.sheet(item:)` 模式。注意 iOS 的 `fullScreenCover` 需特殊处理（ReplayView 仍需全屏）。

### 发现 17：PreferencesMigration 仅在 macOS 初始化

- **文件**: App/ChineseChessApp.swift:41, App/ChineseChessiOSApp.swift:1-20
- **级别**: P1（v3 降级：Luke 裁决，原 P0）
- **问题**: `PreferencesMigration.migrateIfNeeded()` 仅在 `ChineseChessApp.swift`（macOS）的 `init()` 中调用，`ChineseChessiOSApp.swift`（iOS）没有调用。
  
  **iOS 影响面分析**（v2 补充）：PreferencesMigration 的旧 Bundle ID 列表为 `com.hth.ChineseChess` 和 `com.hongtao.ChineseChess`——均为 macOS 历史 Bundle ID。iOS 当前 Bundle ID 为 `com.chinesechess.app`，与这两个旧 ID 无交集。且 iOS 的 UserDefaults 存储在 App Sandbox 内（`~/Library/Preferences/` 路径不可跨 App 访问），即使旧 plist 存在也无法读取。因此 iOS 端实际不受影响。
  
  **降级原因**（Luke 裁决）：已确认 iOS 实际不受影响，当前无功能影响，不符合 P0"影响功能/安全/崩溃"标准。但缺少防御性初始化和注释说明，属于可维护性风险，定 P1。
- **建议**: 在 `ChineseChessiOSApp.init()` 中添加注释 `// PreferencesMigration 不适用于 iOS（从未变更 Bundle ID，且 Sandbox 隔离 plist 访问）`，或者直接加上调用（幂等函数，无副作用）。

### 发现 18：ChineseChessApp.swift 614 行过大

- **文件**: App/ChineseChessApp.swift:1-614
- **级别**: P1
- **问题**: macOS App 文件承担了太多职责：App 入口、CLI 自对弈、CMA-ES 调参、Sheet 路由（16 个 case 的 switch）、复盘卡片生成、PGN 导入、偏好迁移初始化。特别是 `generateReviewCard()` 方法（:564）在 App 文件中创建了 `AnalysisViewModel` 并调用 `CoachExplainer.shared.generateReviewCard()`——这不仅是职责越界，还是 ViewModel 在 App 层被实例化，绕过了正常的 SwiftUI 生命周期管理。
- **建议**: 
  - `SheetDestination` 枚举和路由逻辑提取为 `SheetRouter` 类
  - `generateReviewCard()` 提取为 `ReviewCardService` 或移至 `GameViewModel`
  - CLI 入口（selfplay/cmaes）保持在 App 文件中是合理的
