## 一、版本定位

v3.6.0 是**功能差异化版本**——从"能下"提升到"能学+能玩"：

**学棋线**：
1. **AI 教练**：对局中实时指导，对局后复盘建议
2. **引擎分析**：每步走法 6 级质量分级 + 评估曲线
3. **开局树探索**：交互式开局变化可视化

**闯关线**（2026-06-28 追加，详见 `v3.6.0-quest-restructure.md`）：
4. **残局章节制**：551局重组为7章渐进式解锁
5. **段位奖励实质化**：翰林解锁引擎分析，国手解锁AI教练
6. **成就/每日挑战激活**：成就联动段位，每日挑战做实3种模式
7. **金币经济**（可选）：获取/消费闭环

## 二、技术优势（vs 原设计 2026-01）

原设计基于自研引擎（~2200 Elo），分析精度有限。当前：

| 维度 | 原设计 | 当前（v3.5.0 后） |
|------|--------|-------------------|
| 引擎 | 自研 AIEngine (~2200) | Pikafish NNUE (~3000+) |
| 分析精度 | 位置评估 ±100 分 | Pikafish 评估 ±10 分 |
| 响应速度 | 自研同步搜索 | Pikafish 异步搜索（C API） |
| 走法分级可信度 | 中（弱引擎评分不可靠） | 高（强引擎评分可靠） |

**结论**：技术基础已远超原设计预期，可以做出高质量的教练和分析功能。

**工期**：1 天

#### 0.2 freePlay 用 Pikafish 做防守方

当前 `PuzzleViewModel.aiEngine` 用自研引擎。改为通过 EngineRouter 获取引擎：


#### 1.0a C API 扩展（前置）

**修改文件**：`pikafish_api.cpp` + `pikafish_api.h`

新增接口：
```c
typedef struct {
    int score_cp;      // 厘兵值
    int depth;         // 搜索深度
    char best_move[16]; // 最佳走法
    char pv[256];      // 主变路径
} PikafishEvalResult;

int pikafish_eval(const char* fen, const char* moves,
                  int depth, int time_ms,
                  PikafishEvalResult* result);

int pikafish_multi_pv(const char* fen, const char* moves,
                      int num_lines, int depth, int time_ms,
                      PikafishEvalResult* results, int max_results);
```

**可行性**：Stockfish/Pikafish 内部有 `on_update_full` 回调（含 score/depth/pv），只是 C wrapper 没暴露。扩展技术可行，工作量 2-3 天。

**降级方案**（如果 Spike 失败）：
- MoveQuality 降级为 3 级：好（与 bestMove 一致）/ 一般（合法但非最优）/ 失误
- 评估曲线降级为走法高亮，无数值
- 教练场景降级为走法匹配检测，只检测送子/漏杀/错失杀机

**工期**：2-3 天

#### 1.0b PositionAnalyzer

**新增文件**：`AI/PositionAnalyzer.swift`

核心接口：
```swift
actor PositionAnalyzer {
    func evaluate(fen: String) async -> PikafishEvalResult
    func topMoves(fen: String, moveHistory: [String], count: Int) async -> [PikafishEvalResult]
    func classifyMove(playerMove: String, bestMove: String, bestEval: Int, playerEval: Int) -> MoveQuality
}
```

**MoveQuality 枚举**：
```swift
enum MoveQuality: Int {
    case brilliant = 5  // ≤10 cp 差距
    case good = 4       // ≤50
    case normal = 3     // ≤100
    case doubtful = 2   // ≤300
    case blunder = 1    // ≤700
    case losing = 0     // >700
}
```

**引擎实例策略**（Vera P1-3）：复用 EngineRouter.shared，不新建实例。分析请求排队，避免与对弈冲突。

**工期**：1-2 天

## 五、风险

| 风险 | 评估 | 应对 |
|------|------|------|
| **Pikafish C API 不支持评估值输出** | **高** | **Phase 1 前必须做 1 天 Spike 验证 C API 扩展可行性**。当前 C API 只有 `pikafish_best_move`（返回走法字符串，无 centipawn 评估值），无 MultiPV，无 eval 接口。Phase 1-3 的 MoveQuality 分级、CoachExplainer 场景检测、评估曲线全部依赖评估值。**如果 C API 扩展受阻，Phase 1-3 降级为仅基于走法匹配的简单分析** |
| Pikafish C API 多候选走法 | 中 | 同上 Spike 一并验证。当前 `pikafish_best_move` 只返回单走法 |
| 分析速度慢影响体验 | 中 | 后台预分析（对局中提前分析），缓存评估结果 |
| PositionAnalyzer 引擎实例策略 | 中 | 需决策：复用 EngineRouter（与分析对弈冲突）vs 新建实例（NNUE 48MB×2 内存）。建议复用 + 队列 |
| 评估曲线 UI 复杂 | 低 | SwiftUI Charts 或简单 Path 绘制 |
| 开局树大数据量性能 | 低 | 懒加载节点，初始只展开根层 |

**目标**：1 天验证 pikafish_api.cpp 能否扩展出评估值输出

**需要修改的内容**：

2. Stockfish::Engine 的 `go()` 调用设置 MultiPV
3. 新增 `pikafish_eval()` 接口（同步返回当前局面评估）

**可行性评估**：Stockfish/Pikafish 内部有完整的 info 输出机制（`on_update_no_pv`/`on_update_full` callback），只是当前 C wrapper 没有暴露。扩展在技术上是可行的，工作量约 2-3 天。
