## 1. 现状盘点（要点版，逐页细节见设计单 §1-§4）

macOS 共 **14 个页面场景**（P1-P14，parity V1-V16 + Views 全扫闭合对账，详见设计单 §1 对账行）。

**布局结构现状**：
- 对局/演示/播放三类棋盘页已左右布局化（v6.2 ManagedSplitView 骨架，ratio 连续插值机制现成）；
- 库/分类三页（P2/P7/P13）分类导航**三种实现并存**（横滚标签 / HSplitView / List）——分类语言不统一是最大结构病；
- 学棋/教程并列入口、动线未打通；复盘 P9 藏在 600×700 小 sheet 里；
- 全 app 无统一面板规格/间距/字阶 token，各页各造各的。

**约束痛点**：
1. **大屏利用率**：1280-1920pt 主战场带，高优页 P1-P9 普遍"两侧留白、中间挤"；棋盘面积无下限契约；
2. **信息密度**：演示页右面板三 tab 塞不下（点评滚动失控）；复盘分析面（评估条/分支树）空间不足；
3. **导航层级**：分类入口三种范式，用户在三页间切换要重新学一次导航；
4. **历史病灶**：LJ-1 sidebar 文字挤压系列案、LJ-2 工具栏拥挤系列案（案卷见设计单 §4，均未根治只修表面）。

**洪涛口径对齐**：全域重设计（不只演示/学棋）；桌面布局特性优先；布局一致性优先于平台规范；上方工具栏保留做紧凑适配（→ 两案均保留顶部工具栏，差异在形态）。

## 2. 设计方向两案对比

### 方案 A｜侧边栏导航 + 自适应画布（设计单现方向）

**形态**：NavigationSplitView 双栏骨架——左 sidebar（全局导航：对局/大师库/学棋/残局/探索/设置入口 + 库内分类列）+ 右自适应画布（棋盘页内部再走棋盘+右面板布局）。顶部工具栏退化为紧凑上下文条（保留，按洪涛口径做紧凑适配）。
**优点**：分类导航一次收敛成一种 macOS 原生范式（LJ-1 根治）；导航全局可达，跨域动线（学棋→对局）一步；系统托管 sidebar 语义（分栏记忆/折叠）白拿；v6.2 ManagedSplitView 骨架在画布内部全保留，波及面集中在外壳层。
**缺点**：全局信息架构变更，回归面 = 全 14 页导航路径；sidebar 常驻吃 240-280pt 横向预算，900pt 小窗带更紧。
**迁移成本**：**中**。约 4-5 人日编码 + 全页像素锚重拍（产品代码实测波及：HSplitView 仅 1 处、ManagedSplitView 内部 3 处实现件不动——Ruby R2 已核）。三档面板/插值参数表/迟滞条款设计单均已定稿到可实施。

### 方案 B｜保留工具栏 + 分区画布（渐进改造）

**形态**：不加全局 sidebar。顶部工具栏保留为主导航（现状强化：收纳分层 + 上下文化），页面内部做分区画布治理——分类页收敛为页内左侧分类列（非全局），棋盘页按设计单原则一/二/五调优。
**优点**：变更面小（无全局信息架构改动），回归风险集中在单页内部；小窗带无 sidebar 预算压力；工期短（约 2.5-3 人日）。
**缺点**：导航语言只统一一半——页内分类列仍是"每页自带导航"，跨域动线仍多步；LJ-1 只能页内缓解非根治；后续若再上全局导航（v7+），本期投入部分重做。

### 对比结论与建议

| 维度 | A 侧边栏+画布 | B 工具栏+分区画布 |
|------|--------------|------------------|
| 全域体验一致性（洪涛主诉求） | ✅ 根治 | ⚠️ 半治 |
| 迁移成本/回归面 | 中（4-5d + 全页锚） | 低（2.5-3d + 单页锚） |
| 与 v6.2 骨架兼容 | ✅ 画布内全保留 | ✅ 全保留 |
| v7 演进空间 | ✅ 直接生长 | ⚠️ 可能二次重做 |

**Alex 建议：方案 A**。理由：洪涛定性是"完整用户体验规划"而非局部修补，B 的省是伪省（导航半治 = 未来重做风险）；A 的额外成本主要在外壳层一次性投入，且 R1/R2 两轮评审已按 A 打磨到实施级，沉没质量现成。**最终由洪涛拍板。**

### 与 v6.3 交付链防线兼容性（两案通用）

- v6.3 第四层 manifest（含图标/xcstrings hash）直接服务 v6.4——布局改造不动资产集，防线零冲突；
- v6.3 L3 真实性纪律（像素锚真实组件 + 三图入档）正是 v6.4 像素锚治理的依赖件，v6.4 复用不重造；
- v6.3 不动 M1 引擎语义；v6.4 纯布局层，不触碰引擎面——互不抢占；
- 唯一交叠点：v6.3 SEL-1/C1 测试入库产生的像素锚基线，v6.4 改版后需重拍——设计单原则六已把"改版 = 锚重拍"写进规约，属预期成本非冲突。

## 3. v6.4 主题版本内 Milestone 切分（复用 v6.1 M1 治理模式）

治理模式沿用 v6.1 M1 验证过的骨架：**每 M = 设计单细化 → 编码 → 像素锚+参数 dump 双件验收 → Vera/Ruby 审查门禁**；布局版把 SPRT 换成"双向扫掠单调断言 + 档位锚"（设计单原则六），playbook 判停框架复用。

| M | 内容 | 验收锚 | 工期 |
|---|------|--------|------|
| M0 | 布局基建：LayoutSpec 单源常量 + LAYOUT_DUMP 通道 + token 表（面板三档/间距/字阶） | dump 流可消费、常量单源审计通过 | 1d |
| M1 | 外壳改造（方案 A 时）：全局 sidebar + 工具栏紧凑化；B 时：工具栏分层 + 页内分类列 | LJ-1/LJ-2 根治 + 导航动线像素锚 | 1.5-2d |
| M2 | 重点区 A/B：演示页 P4 右面板密度重排 + 学棋 P5+P6 动线打通（1440×900 零滚动验收） | 单屏零滚动 + 信息带 ≤25% | 2d |
| M3 | 高优余面：P1 三栏 / P2 播放密度 / P8 棋树 / P9 复盘升级（760×820） | 各页原则一面积断言全绿 | 1.5d |
| M4 | 低优页 P10-P14 套 token + 全域双向扫掠收口 | up/down-sweep 分跑全绿 + 三图入档齐 | 1d |

总量 ~7-8 人日（方案 B 砍 M1 外壳量约省 1.5-2d）。每 M 独立可收口可回退，防"改一半的全域布局"。
